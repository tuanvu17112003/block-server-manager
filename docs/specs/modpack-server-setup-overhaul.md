# Specification — Modpack Server Setup Overhaul

## Goal

Replace the separate, error-prone modpack setup implementations with one reviewable installation pipeline for new modpack servers and safe reapplication/update flows, while preserving the app's existing server runtime and Start behavior.

## Scope decisions

- **CurseForge:** keyless, author-provided server ZIP only. Detect client-export ZIPs and explain the supported SERVER-pack route; do not add API keys, API resolution, client-export synthesis, or bundled credentials.
- **Modrinth:** remote project/slug/ID/URL plus exact version pin, and local `.mrpack` file input. IDs and resolved version pins are recorded before mutation. A local index must include the format-required `versionId`, but that author-controlled text is display metadata only and does not establish provider ownership or archive authenticity.
- **Loaders:** Vanilla, Fabric, Forge, and NeoForge for new modpack installs. Quilt is a disabled/planned placeholder with a clear reason; existing saved Quilt servers keep their current behavior. Standalone Paper server creation remains unchanged and outside this modpack pipeline.
- **Reuse:** use upstream implementation policies as references; do not bundle an external CLI, Docker service, or candidate application.
- **Non-goals:** automatic client-only-to-server conversion, fuzzy version substitution, imported script execution, silent dependency injection, and automatic changes to existing worlds or EULA state.

### CurseForge server-archive support boundary

| Detected input | Policy |
|---|---|
| Validated complete Forge or NeoForge server archive | Install only when exact Minecraft/loader metadata and parsed launch/runtime artifacts agree. |
| Recognized ServerPackCreator Fabric archive selected through the author-provided SERVER ZIP lane | Install only with the documented root manifest shape, nonempty `files` inventory, exact `minecraftVersion`, `modloader=Fabric`, exact `modloaderVersion`, safe payload paths, and the verified Fabric runtime path. Accept one outer ZIP only when it contains exactly one inner archive matching this same shape. Never synthesize this input from a client export. |
| CurseForge client export (`manifest.json` + overrides, no validated server runtime) | Classify and explain that this keyless workflow requires the author's SERVER file. |
| Generic `server_files/` templates; deeper or multiple nested archives; other Fabric layouts; Quilt; Paper; vanilla/ambiguous; scripted; or unknown layouts | Classify with a specific reason and reject until a separate exact parser and fixture gate is approved. Never infer support from filename or extension. |

## Required pipeline

1. **Resolve and plan:** classify source; resolve exact pack and loader pins; write `install-plan.json`; make no server-directory mutation before validation and preflight. The audit JSON is never the authority used to install. Build the active in-memory plan again from the pinned provider response/archive and explicit per-file UI choices; on resume, rederive from the same exact pin and archive fingerprint. For a remote Modrinth `.mrpack`, verify its API-declared SHA-1, SHA-512, and size. For a local `.mrpack` without a trusted external digest, record calculated archive hashes as a source fingerprint (not an authenticity claim) and still verify every manifest file's SHA-1, SHA-512, and size.
2. **Validate inputs:** validate manifests, ZIP paths, duplicate normalized paths, entry/expanded-size bounds, symlinks/reparse points, disk space, target writability, the selected Java executable and required major, and name/port conflicts. Paths reject traversal/absolute/drive/UNC forms, separators and case aliases, Win32-invalid characters and reserved device names, and paths/components beyond configured limits. Bind the persisted target to the selected DB server and exactly `<app-data>/servers/<server-id>`; recompute and enforce the combined absolute path length (<240 characters), canonical containment, and reparse checks before every write/delete. A local `.mrpack` root index requires a nonempty `versionId`, treated only as untrusted display metadata. For a remote Modrinth archive, verify API-declared SHA-1, SHA-512, and size; for a local archive, record a calculated fingerprint and validate ZIP structure without claiming trusted archive authenticity. For each indexed Modrinth file, verify manifest-declared SHA-1, SHA-512, and size in either input mode. Require HTTPS and revalidate every redirect hop against the explicit provider allowlist (`cdn.modrinth.com`, `github.com`, `raw.githubusercontent.com`, `gitlab.com`); allow at most three redirects. Apply the same per-hop scheme/host rule to loader metadata and artifacts using their source-specific official allowlists.
3. **Select files:** use a shared `client|server|both` model. Modrinth required entries are included, `env.server=unsupported` is excluded, absent `env` defaults to retain with a warning, and optional entries are shown as checkboxes with keep selected by default. Conflicting signals require a visible user choice; unattended installs stop. Record every decision.
4. **Download and verify:** use bounded concurrency/retries, ordered allowed URLs, exact declared sizes and hashes, and remove partial files on failure. Required download failures stop with path, attempted sources, and integrity evidence. Optional failures may skip only after explicit policy and report them. For each archive source, preflight temporary-volume space, create a bounded private snapshot while calculating SHA-1 and SHA-512 from the same byte stream, and keep it protected from writes/deletes while classifying/parsing it. Remote Modrinth snapshots must match provider metadata before further processing. Check cancellation throughout copying and at each later stage boundary. Do not launch an external hash utility; never include files awaiting a user choice in download work. Loader metadata and artifact requests also validate each HTTPS redirect hop against source-specific official hosts, cap the chain at three, use the system-directory curl executable, and disable curl's default configuration before requests.
5. **Prepare loader:** resolve exact compatible metadata from official Mojang/Fabric/Forge/NeoForge sources. Install or reuse only when completeness checks pass; parse generated args files and required libraries. Never substitute a nearest/latest loader build.
6. **Stage and merge:** apply base overrides before server overrides; never extract client overrides. Parse but do not execute pack scripts. Store pipeline file ownership and installed hashes in an additive SQLite `managed_server_files` registry; write `managed-files.json` as an audit snapshot, never the sole deletion authority. On update, back up first, then remove only old-managed files absent from the new plan and confirmed by the registry; keep untracked files. The update transaction must reject protected paths from overwrite/stale deletion: `world/`, `eula.txt`, `logs/`, `backups/`, manager report/plan files, and the `user_jvm_args.txt` file. Merge only manager-owned keys in `server.properties` and retain user keys. If a managed file's current hash differs from its recorded installed hash, report a conflict and preserve the edit unless the user explicitly chooses replacement after backup. Keep the most recent two backups. Log each overwrite, skip, preserve, and stale-file removal.
7. **Configure launch:** parse pack and loader launch files; use deterministic precedence; show exact executable, argv, CWD, and selected Java before first start. Use argument-list process APIs, with server root as CWD.
8. **Validate, publish, report:** validate startup inputs, publish only from same-volume staging, roll back on failure, and write `install-report.json`, `managed-files.json`, and a reusable `launch-config.json`. EULA remains explicitly user-controlled. Startup readiness is recorded only after loader initialization and the Minecraft `Done (...)!` line; EULA prompt is `awaiting-eula`, not failure. If startup fails, classify known signatures from exit status, `latest.log`, and crash reports without changing pack files. Diagnostic files are opened read-only and bytes are consumed only after the opened handle is confirmed beneath the bound canonical server root; an incomplete bounded crash-report scan is disclosed in the diagnostics.

## Safety and compatibility rules

- `env.server=unsupported` files are not auto-installed. A missing hard dependency does not trigger downloads outside the selected pack; show the dependent mod, missing ID, skipped path when known, and stop before publication unless the user resolves the conflict through an explicit supported choice.
- Runtime diagnostics distinguish at least: Fabric/Forge missing dependency tables; corrupt JAR/`zip END header not found`; client-only/`DEDICATED_SERVER` leakage; Java `UnsupportedClassVersionError`; mixin/apply conflicts naming both mods when present; invalid launch arguments/libraries; EULA-pending; and failure to reach `Done (...)!`. Ambiguous mixin/bootstrap failures are reported without choosing a mod to remove. No automatic dependency injection, mod removal, loader downgrade, Java downgrade, or heap increase.
- The initial runtime classifier diagnoses and preserves the failed server for review; automatic quarantine or one-click repair is out of scope until separately specified.
- Modrinth override order is `overrides/` then `server-overrides/`; `client-overrides/` is never extracted.
- Archive and downloaded contents remain untrusted data. No command, batch, shell, PowerShell, or Java code from the archive is executed.
- Existing EULA, Java validation, cancellation, progress, app-data staging, persistence, and Start contracts remain in force.
- Install reports include included/skipped/optional/failed files, hashes, source pins, loader evidence, warnings, and validation state.
- Updates retain untracked user files, preserve worlds, back up overwritten user-managed paths, remove stale pipeline-owned files, and record rollback evidence.
- The SQLite ownership registry is authoritative and transactionally bound to server ID and canonical app-data directory; the JSON manifest must match it before cleanup. If records are absent/mismatched, fail safe and do not delete. Legacy servers without ownership records require a user-reviewed preview/adoption before future stale-file cleanup.
- Keep the two most recent successful backups. Preserve `world/`, EULA acceptance, and user-owned `server.properties` keys on update; restore the prior tree and database state on rollback.

## Acceptance criteria

- [ ] One shared typed install plan and explicit stage/state model drives both providers.
- [ ] Persisted plans bind `target.directory` to the current selected server ID under app data; a changed/foreign target is rejected before filesystem access.
- [ ] Editing `install-plan.json` cannot override provider-required/server-unsupported policy; the active plan is rederived from exact source data, and user overrides are accepted only for rederived conflict paths with an explicit UI choice.
- [ ] CurseForge SERVER ZIPs are classified by content; client exports and invalid archives get actionable, keyless explanations.
- [ ] Remote Modrinth and local `.mrpack` installs resolve exact version IDs and validate project ownership, manifest shape, file paths, hashes, and server overrides.
- [ ] Remote `.mrpack` archive hashes use the Modrinth version metadata; local archive hashes are recorded only as fingerprints unless a trusted expected digest is available.
- [ ] Optional file choices are visible and recorded; server-unsupported files remain excluded; conflicts and missing hard dependencies have actionable diagnostics.
- [ ] Exact Vanilla/Fabric/Forge/NeoForge runtime builds are installed or reused only with completeness evidence; Quilt remains visibly unavailable for new installs.
- [ ] Staging, cancellation, backup/merge, promotion, rollback, and world preservation satisfy the transaction checklist.
- [ ] Path tests cover traversal, drive/UNC/absolute paths, aliases, Win32-invalid characters, reserved device names (including superscript COM/LPT forms), and configured component/total length bounds.
- [ ] Updates remove stale pipeline-owned files without deleting untracked/user-modified files; user conflicts are backed up and preserved unless explicitly replaced.
- [ ] `managed_server_files` is migrated additively, bound to the server ID/path, and updated in the publication transaction; the JSON manifest is an audit snapshot only. Missing/mismatched ownership records never authorize deletion, and legacy servers require reviewed adoption.
- [ ] Protected paths (`world/`, EULA, logs/backups, JVM args, manager artifacts) cannot be overwritten or stale-deleted during update; only manager-owned `server.properties` keys change.
- [ ] Launch configuration is parsed, displayed, and saved; imported scripts are never executed; explicit EULA behavior is unchanged.
- [ ] Setup and startup validation produce `install-plan.json`, `install-report.json`, `managed-files.json`, and `launch-config.json` with reproducible pins and per-file decisions.
- [ ] Startup diagnostics distinguish missing dependencies, corrupt files, client-only leakage, Java mismatch, mixin conflict, invalid launch data, EULA-pending, and no-`Done` timeout without blind repair.
- [ ] Historical startup diagnostics verify opened-handle containment before reading, and identify when the bounded crash-report scan did not cover the full directory or an enumerated report disappears before it is read.
- [ ] Pinned regression cases cover: CurseForge server-pack file 9094783 (Prominence II 4.1.3; use the original ZIP only if already available, otherwise a generated format fixture); Modrinth Better MC Fabric project/version `shFhR8Vx`/`M5BnAIQy`; Modrinth Better MC Forge `4BV47HRn`/`bdRIjRgs`; invalid/truncated/HTML CurseForge downloads (no promotion); local `.mrpack`; per-file hash/size/path/redirect failures; optional and conflicting environment entries; missing hard dependency; exact loader unavailable/incomplete; update stale-file cleanup with user/untracked retention; rollback after promotion failure; explicit EULA-pending; and `Done` readiness. Fetch and record full artifact hashes before any claim; the listed research seeds are candidates, not verified execution results.
- [ ] Independent review passes and the pinned success/negative matrix is executed before the old paths are removed.
