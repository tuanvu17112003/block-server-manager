# Tauri→Electron parity matrix

Scope: dormant Rust reference `src-tauri/src/**` (44 files, ~32k LOC) vs Electron main (`electron/**`, ~4.5k LOC) and renderer (`src/**`).
Method: read `lib.rs` first, then every `#[tauri::command]`, each command's Rust contract, the Electron registration/service, and the renderer call site. No builds/tests were run. Confidence tags: **[H]** both sides read; **[M]** code-reasoned, not executed; **[L]** assumption.
Status meanings: **OK** contract preserved; **PARTIAL** works but drops validation/fields/events or changes semantics; **BROKEN** produces wrong/broken behaviour for a reachable UI path; **MISSING** no Electron counterpart; **NEW** no Rust counterpart (Rust stub or added feature, so Rust-parity is N/A).

## Executive summary

- The Rust app only ever registered **35 commands** (`src-tauri/src/lib.rs:88-124`). Three more `#[tauri::command]` fns are defined but never registered and are superseded dead code (`installer/mod.rs:650,748,1067`). Backups/worlds/players/metrics/content/rcon are **Phase 7–9 stubs with no Rust implementation** (`src-tauri/src/{backups,worlds,players,metrics,content,rcon}/mod.rs:1`), so the Electron management/content wave is *new* functionality, not a port.
- Electron registers **65 handlers** (`electron/ipc.ts:25-48`, `runtime.ts:54-131` + service `handlers()`): all 35 Rust names plus **30 new commands** (settings/port/folder, players 3, worlds 7, backups 7, metrics 2, content 6, `curseforge_inspect_project`). No Rust command is unregistered in Electron; every Rust name still has a renderer call site in `src/tauri.ts` (though `ping`, `server_get`, `servers_create` are dead from the UI).
- Command status count vs Rust: **OK 6 · PARTIAL 21 · BROKEN 8 · MISSING 0**. Biggest broken paths: **Paper servers cannot be installed** (no `paper` branch in `installLoader`, `installer/core.ts:227-278`), **Java detection/validation DTO drift blanks the Java UI and clears saved overrides** (`runtime.ts:55-68` vs `tauri.ts:225-230`), **Kill shows `crashed`** (`server-process.ts:248-251`), **Create's install-report card dereferences a field the backend never returns** (`Create.tsx:2394` vs `pipeline.ts:125`, no error boundary in `App.tsx`), **CurseForge staged dates are 1000× off** (`staging.ts:55` → `Create.tsx:1682`).
- Lifecycle semantics changed materially. Rust stages installs in `installer-staging/<uuid>` and publishes with an atomic rename + DB insert only after validation (`servers/mod.rs:282-423`); Electron creates the JSON row first and installs in place, deleting on failure (`runtime.ts:87-118`). Rust refuses start on EULA mismatch / occupied port / missing launch files (`servers/process.rs:518-561`); Electron only checks the JSON flag, rewrites `eula=true`, and silently re-allocates the port (`server-process.ts:95-103`).
- Process identity and crash safety are weaker: Rust writes `server.lock`, verifies `java.exe` **and** the `-Dtestmultiai.server.id=<id>` command-line marker before reaping orphans, kills the tree with `taskkill /T /F`, and blocks 3 s on window close (`servers/process.rs:1559-1674,1751-1777`); Electron persists only a PID, checks `tasklist` for "java", kills the direct child only, and its `before-quit` stop-all is not awaited (`main.ts:121`, `server-process.ts:60-84,248-251`).
- Persistence switched SQLite→JSON as approved (`docs/electron-port-plan.md:7`), but with concrete losses: no transactions (whole-file read-modify-write, `store.ts:118-122`), no unique port constraint, no `managed_server_files` ownership/hash table (`db/mod.rs:85-101`), no `jobs` table, history is a global 500-line string list instead of 100 rows/server with timestamps (`store.ts:247-256` vs `servers/console.rs:14-16,85-105`).
- Install/job telemetry is thinner: Rust emits `job://progress/{id}` with `{progress, stage, log, bytesDownloaded, bytesTotal}` and writes an `install-report.json`; Electron emits mostly `{progress, stage}` only (`jobs.ts:27-29`), so Create's installer-log pane and byte counters stay empty, and the UI text promising `install-report.json` (`Create.tsx:2439`) is false.
- Security checks that existed in Rust are dropped in Electron: command newline validation, per-command server-id validation, realpath/reparse checks for log tailing, 2 GiB/reparse/dedup/atomic staging checks for picked ZIPs, Adoptium SHA-256 + install lock, and CurseForge-browser navigation allowlisting (`server-process.ts:256-277`, `ipc.ts:47`, `curseforge-staging.ts:19-45`, `installer/core.ts:192-209`).
- Verdict: the port is functionally complete for the demoed happy paths (vanilla Fabric/Forge/NeoForge create/start/stop, Modrinth/CF engines) but **not feature-parity complete**; the gaps concentrate in validation/security policy, install atomicity, lifecycle/event fidelity, and renderer↔backend DTO drift that the backend-only E2E (`electron/e2e.ts`) cannot see.

### Renderer adapter and verification gates (why the drift escaped)

- The renderer has four backend branches: Electron (`window.electronAPI`), Tauri, runtime-configured HTTP (`/rpc`+`/events`), and a stub; `hasBackend()`/`isElectron()` select them (`tauri.ts:16-47,450-484`). Electron results are cast to renderer-declared DTOs (`invokeElectron<T>`, `tauri.ts:21-33`) with **no runtime validation**, and IPC handlers are typed `Promise<unknown>` (`ipc.ts:16`), so a declared type cannot catch a backend payload that omits fields.
- Error plumbing is preserved: main returns `{__ipc, ok, value|error}` (`ipc.ts:94-115`), preload unwraps and re-throws JSON `{code,message}` (`preload.ts:13-22`), renderer rebuilds `AppError` (`tauri.ts:21-33`). Non-strict `invokeOrStub` still falls back to null only on the Tauri path (`tauri.ts:450-464`); `invokeRequired` always throws.
- Gates are backend-only: `--selftest` calls the handler map (`ipc.ts:120-146`), `--ipctest` drives preload→ipcMain plus a UI smoke (`main.ts:88-117`, `ipc-test.ts`), `--e2e` calls the handler map and installer engines **without rendering React** (`electron/e2e.ts:1-4,16-20`), `--mgmttest` covers new services (`main.ts:63-71`, `mgmt-test.ts`). The pipeline-report crash (#1), Java DTO drift (#2), and CF date unit (#4) are all in that blind spot; `npm run build`/`tsc` cannot catch them because the renderer type is asserted, not verified. [H]

## Feature-area parity

### Server lifecycle & process identity — PARTIAL
- Rust validates EULA from both DB and `eula.txt` and refuses to start otherwise (`servers/process.rs:224-244,516-531`); Electron checks only the JSON flag and **writes** `eula=true` before spawning (`server-process.ts:95-96`). Settings reports EULA “accepted” from mere file existence (`properties.ts:234`), so a manually reverted `eula=false` is displayed accepted and then overwritten. [H]
- Rust fails closed on a port taken since create (`process.rs:533-543`); Electron silently picks the next free port and persists it (`server-process.ts:97-103`) — same intent as the port-plan note but a user-visible semantic change.
- Rust validates launch shape (`resolve_launch_mode`, `process.rs:259-330`) and Java before spawn; Electron `launchCommand` (`core.ts:300-315`) accepts a `run.bat`, a loader jar or `server.jar` with no argument-file verification and throws an uncoded `Error` (IPC code becomes `internal`).
- Status model: Rust `starting` (immediate) → `running` after 1 s grace, and a `crashed` terminal only for unrequested/non-zero exits (`process.rs:1255-1376`); Electron `running` only on the `Done (` log marker with a 10-minute watchdog, plus an 8-round auto-fix loop (`server-process.ts:117-167,197-235`). Kill misreports `crashed` (#31). Stop grace 30 s vs 15 s.
- Process identity/orphans: Rust `server.lock` + `taskkill /T /F` + CIM command-line marker verification (`process.rs:638-646,1617-1777`); Electron `.msm-server.pid` + `tasklist` “java” substring + `process.kill` of the direct child (`server-process.ts:60-84,248-251`). PID reuse and tree descendants are not guarded; no Windows job object equivalent.
- Shutdown: Rust blocks up to 3 s and kills survivors on main-window close (`lib.rs:73-87`, `process.rs:1559-1612`); Electron’s `before-quit` fires `void appRuntime.shutdown()` and does not preventDefault (`main.ts:121`), so exit can race the 30 s per-server stops → orphaned `java` (reaped only on next boot). [H]
- Concurrency: Rust has a start-reservation set and single finalizer (`process.rs:146-220,1322-1376`); Electron’s `running` map entry is deleted between auto-fix rounds, so a second `server_start` can spawn concurrently with the running loop. [M]

### Console streaming & history — PARTIAL
- Live stdout/stderr → `server://log/{id}` with bare string payload is preserved (`process.rs:88-101` vs `server-process.ts:205-219`); Rust truncates lines to 4096 bytes and drops `\r` (`process.rs:752-801`), Electron splits on `\n` with no byte cap. Ring buffer 5000 lines vs UI retention (`logs.ts`).
- History persistence differs: Rust records commands in the SQLite `console_command_history` table and tails the server's own `logs/latest.log`; Electron writes its own `logs/msm-console.log` (10 MB rename rotation, `server-process.ts:174-184`) and tails that. Post-restart history therefore covers only MSM-captured lines, not pre-port/pre-app output. [H]
- Read-hardening lost: Rust canonicalizes server/log dirs, rejects reparse/symlink/FIFO, uses `FILE_FLAG_OPEN_REPARSE_POINT` + `GetFinalPathNameByHandle` and 16 MiB/10 000-line caps (`servers/console.rs:107-248`); Electron `fs.readFileSync` on a renderer-supplied id with no `validate_id`/realpath check (`server-process.ts:267-277`). [H]
- Rust emitted `server://readiness/{id}` snapshots with diagnostic evidence (`process.rs:99-113`); Electron has no counterpart and the renderer has no subscription (`tauri.ts:695-733`) — crash diagnostics/pointers are lost.
- Command history: per-server 100 with timestamps (Rust) vs global 500 strings (Electron); UI history loads per server but cap is global. [H]

### Store/DB — PARTIAL (approved architecture change, concrete losses)
- SQLite (`db/mod.rs:18-101`): `servers` with `UNIQUE(name)`, `UNIQUE(port)`, FK cascades, `backups`, `worlds`, `jobs`, `settings`, `console_command_history`, `managed_server_files` (ownership + sha1/sha512 + plan id, used by the pipeline transaction). Electron JSON (`store.ts:66-86`) stores `servers`, `settings`, `consoleCommandHistory`, `backups`, `backupSchedules`, `pendingWorlds`; no worlds/jobs/ownership tables, no unique port, no FKs.
- Writes are whole-file `writeFileSync(tmp)+renameSync` (`store.ts:118-122`) with read-through reload (`:97-116`); handler instances are independent, so concurrent read-modify-write loses updates (e.g. two installs or install + status write). Rust serialized a single connection behind a mutex (`db/mod.rs:13-15`). [M]
- Migrations: additive v1/v2/v3 batches, idempotent (`db/mod.rs:103-108`); Electron hard-codes `schemaVersion:2` on load and has **no migration code** (`store.ts:103-112`). Existing Tauri `app.db` data is not imported at all (JSON store starts empty) — a user-visible “servers disappeared after migration” risk. [H]
- Timestamps: Rust `to_rfc3339` (server-local offset), Electron `toISOString` (Z); both parseable, backup filenames differ (`store.ts:151` vs `servers/mod.rs:169`).
- Backup metadata: Rust columns `size_mb REAL`, `kind`, `note`, `created_at`, cascade delete (`db/mod.rs:36-45`); Electron `bytes`, same kind union, note, createdAt, filtered in `deleteServer` (`store.ts:164-171`). Equivalent for backup list, but backup IDs/files are only in JSON; a deleted/corrupt JSON orphans ZIPs (and `servers_delete` removes backup files first, `ipc.ts:41-45`).

### Java provisioning & versions/loaders — BROKEN/PARTIAL
- Java DTO drift and validation loss are the largest UX defect: see #7/#8. `java_ensure` keeps the Rust-shaped return and works.
- Rust `required_java_major` uses Mojang metadata with an offline fallback table and maps 1.17→16 then installs 17 (`java/mod.rs:207`, fallback tests `java/mod.rs:1341-1371`); Electron `requiredJavaMajor` consults metadata then a small table (`core.ts:148-164`) — close enough, but no offline-vs-online distinction tests and no supported-major whitelist.
- Rust detects only 64-bit runtimes of majors `[8,17,21,25]`, inspects architecture, uses a 5 s validate timeout (`java/mod.rs:18,21,185-205`); Electron parses `java -version` via `spawnSync` with no timeout, no arch check, matches exact major only (`core.ts:167-191`). A hanging or 32-bit java binary can stall/mislead detection. [M]
- Adoptium: Rust verifies SHA-256 with `certutil`, checks 512 MiB headroom, uses a global install lock and curl/certutil hidden processes (`java/mod.rs:22,1213-1237`); Electron verifies size only and `rmSync` + extract with no lock (`core.ts:192-209`) — concurrent ensures can clobber `<runtime>/temurin-N`.
- Versions/Paper/loader catalogue: see #10–#12. Paper install path is outright missing (`core.ts:227-278`); NeoForge coordinate normalization matches the port plan’s fix (strips `mc-` prefix) but has no catalogue/legacy verification.

### Installers & modpack pipeline — PARTIAL
- Rust validates install request (name ≤64 + no `=`/CR/LF, loader whitelist, MC version syntax, RAM 512–65536, Java required, Windows x64) and preflights name/port under the DB lock (`installer/mod.rs:1080-1142`, `servers/mod.rs:216-240`); Electron `server_install` does none of this (`runtime.ts:87-118`) — the renderer is the only validator. [H]
- Atomicity: Rust stages every install under `installer-staging/<uuid>` with `installer.log`, `ensure_safe_staging`, then renames into `servers/<id>` and inserts the row, rolling the folder back on failure (`servers/mod.rs:263-423`). Electron writes directly into `<dataRoot>/servers/<id>` from the start and deletes the record+folder on failure (`runtime.ts:87-118`, `pipeline.ts:121-201`) — no “complete-or-nothing” guarantee if the process dies mid-install, and rows are visible to `servers_list` while installing. [M]
- Hash/size/ownership: Rust verifies sha1/sha512/size and records `managed_server_files` per installed file (schema v3, `db/mod.rs:85-101`); Electron verifies hashes on downloads (`core.ts:42-62`) but records only `msm-install.json` path lists (`pipeline.ts:203-205` sidecar; `server-process.ts:86-88` reads it) — no post-install hash verification/repair, no tamper detection, no ownership for future update/remove operations.
- Pipeline DTO/hooks: Rust `PipelinePreview.plan` is the validated `InstallPlan` (`plan.rs:45-84`, `model.rs:149-219`); Electron exposes only `{loader, fileDecisions}` (`pipeline.ts:107`) with `reason` values limited to `required/userChoice/serverUnsupported/missingEnvironmentRetained` — renderer type also allows `optionalDefaultKeep`/`conflictingSignals` (`tauri.ts:311-317`), which are never produced. Curated L1/L4 resolution and sidecar L2/L3 boot defense are ported (`curated.ts`, `server-process.ts:109-166`), matching the port plan.
- Quilt: Rust rejects Quilt for new installs (ADR-0005; `installer/mod.rs:1087-1091`, `plan.rs:30-32`); Electron `LOADER_DTO` maps `quilt: 'Quilt'` (`pipeline.ts:38`) and `installModrinth` can install quilt loader (`modrinth.ts:72,139`) — ADR-0005 policy violated on the modpack path.
- CF policy: Electron embedded browser/one-click key mode are delivered (`curseforge-staging.ts`, `installer/curseforge.ts:133-235`), route A/B classification ported, but staging copy hardening and navigation allowlist were dropped (see #23/#26).

## Cross-boundary bugs (UI ↔ Electron ↔ Rust drift)

1. **Create install-report card dereferences a field the backend never returns [H].** Renderer expects `PipelineInstallReport.loader.minecraftVersion` (`tauri.ts:392-404`, rendered `Create.tsx:2394-2396`); `pipeline.ts:125` builds the report as `{status, stages, files, warnings, errors}`. `pipelineReport.loader` is `undefined` → TypeError during render; `App.tsx` has no error boundary (whole window blanks) after any pipeline install attempt. `planId` also renders as `undefined`.
2. **Java candidates use `javapath` not `path` [H].** `runtime.ts:59` returns `detectJava` output (`core.ts:166-191`); renderer `JavaCandidate` requires `{path, architectureBits}` (`tauri.ts:225-230`). Affects `Create.tsx:816,849,905,1048,1162`, `Settings.tsx:120,171,205,233,382`: blank Java path, “saved” toast while `servers_set_java_path` stores `null`, and `javaSelected.path !== javaPath` gates can permanently disable install when an override is typed (`Create.tsx:1024,1204,2355`).
3. **Kill → `crashed` [H].** `server-process.ts:248-251` does not mark the stop as user-requested; `wireWatch` exit path (`:220-227`) then emits `crashed` + crash toast (`store.tsx:449-453`). Rust set `stopping` first (`process.rs:1473`).
4. **CurseForge staged date unit [H].** `staging.ts:55,67` returns `mtimeMs`; renderer multiplies by 1000 (`Create.tsx:1682`); Rust returned seconds (`curseforge_import.rs:244-248`).
5. **EULA policy weakened [H].** Electron start rewrites `eula=true` from the JSON flag (`server-process.ts:95-96`) and Settings infers acceptance from file existence (`properties.ts:234`); Rust required DB **and** file truth (`process.rs:516-531`). A `eula=false` file can be shown accepted and replaced.
6. **`servers_set_java_path` unvalidated + usable while running [H].** `ipc.ts:47` vs Rust validation/stopped guard (`cmds/servers.rs:48-61`); combined with bug #2, Settings can silently clear a working override.
7. **Paper create is dead [H].** `runtime.ts:27` maps `Paper→'paper'`, but `installLoader` (`core.ts:227-278`) has no paper branch; UI advertises Paper (`Create.tsx:1462`, `versions.ts:29`). Install always fails at stage “installing paper”.
8. **Pipeline preview reuse/double-install [M].** `pipeline.ts:122-186` keeps the preview in the map until success and never marks it consumed before work; two concurrent `modpack_pipeline_install` calls can create two servers for one review. Rust removed the preview first (`commands.rs:576-585`) and reinserted only on pre-mutation failure.
9. **Install telemetry promised but absent [H].** Create renders `payload.log`/`bytesDownloaded` (`Create.tsx:1234-1246,1058-1066`), but Electron emits almost only `{progress, stage}` (`jobs.ts:27-29`, `runtime.ts:96-110`, `pipeline.ts:143`), so the installer-log pane stays at “Waiting for installer output…” and byte counters stay empty. Rust emitted `log` and byte counts (`installer/mod.rs:5416-5433`).
10. **False `install-report.json` copy [H].** `Create.tsx:2439` says the full report is saved in `install-report.json`; Electron never writes it (only `msm-install.json`, `pipeline.ts:203-205`). Rust wrote it via `report::INSTALL_REPORT_FILE`.
11. **Registered-but-never-called handlers / dead renderer APIs [H].** `system_disk` (`metrics.ts:282-287`), `ping`, `server_get`, `servers_create` have no UI caller; `tauriServers.get`, `tauriMetrics.disk`, `store.createServer` are dead (`tauri.ts:487,495,496,551`; `store.tsx:329-344`). Conversely every Rust command still has a renderer export, so nothing a Rust-era UI called is unreachable.
12. **Exit/timeout contract drift [H].** Rust commands “return fast” and completion arrives via events (`cmds/process.rs:3-7`); Electron `server_start/stop/restart` resolve only when the process reaches a terminal/ready state (`server-process.ts:90-167,237-253`), up to 10 min × 8 auto-fix rounds. Any UI spinner/awaiting code that expects fast ack will hang; `stop_all` at quit is fire-and-forget (`main.ts:121`).
13. **`metrics://tick/{id}` vs `metrics://{id}` [H].** Rust helper name (`util/events.rs:32-35`) differs from Electron channel (`metrics.ts:227,253`); no Rust implementation existed, so only a naming-contract inconsistency for future backends/HTTP SSE.
14. **`server_open_folder` traversal [M].** `properties.ts:271-281` joins raw `sub` onto the server dir; `sub: "../.."` opens arbitrary folders (no write, but a policy regression vs Rust’s id/path validation).
15. **No id validation anywhere in Electron IPC [H].** `logs_tail`, `curseforge_inspect_zip`, `worlds_*`, `backups_*`, `content_*` join renderer-provided ids/names onto data paths; store lookup protects most, but `tail()` (`server-process.ts:267-277`) and `inspect_zip` (`staging.ts:83-88`) do not require the entity to exist first.
16. **Overview world size never hydrated [H].** `Server.worldSizeMb` defaults to 0 (`store.tsx:68`) and `serverFromDto` (`store.tsx:73-108`) never fills it; `Overview.tsx:82` renders it as “0 MB” for every server even though the backend computes sizes (`worlds.ts:16-22,71-110`, `WorldDto.sizeBytes` in `tauri.ts:120-126`). The Worlds tab shows real sizes; the Overview does not. Cosmetic but a visible new-frontend wiring gap.

## Audit status

**Scope.** Read-only Tauri→Electron parity for `src-tauri/src/**` (44 Rust files, ~32k LOC) vs `electron/**` and `src/**`: the 35 registered Rust commands plus 3 unregistered command fns, 30 Electron-only commands, all event channels, and the feature areas requested (lifecycle/process identity, console, store/DB, Java/versions, installers + pipeline, backups, worlds, players, metrics, content, RCON, security, settings/defaults, i18n). Only `docs/audit/05-parity-matrix.md` was written.

**Method limits.** Static reading only: no `cargo`, npm build/dev/start, Electron binary, or tests were executed (Lead runs gates), so runtime failure modes are reasoned from code, not reproduced. Confidence: **[H]** both sides read at the cited lines; **[M]** code-reasoned with a plausible runtime hazard; **[L]** assumption/unverified. The Rust reference is dormant and its pipeline/transaction modules (~11k LOC) were read at contract level only (task-3 covers installer deep-dive; task-4 covers management internals). Claims about gate coverage come from reading `electron/e2e.ts`, `ipc-test.ts`, `mgmt-test.ts`, not from running them.

**Final tally (35 Rust-registered commands).** OK **6** · PARTIAL **21** · BROKEN **8** · MISSING **0**. Plus 3 Rust commands defined but unregistered (dead), and **30** Electron-only commands (29 UI-wired; `system_disk` unwired). Registered handlers with no UI caller: `ping`, `server_get`, `servers_create`, `system_disk`.

**Incomplete-migration verdict.** The migration is complete for the shipped demo paths but not parity-complete. *Genuinely missing* (was implemented in Rust, absent in Electron): staged/atomic install publication, pipeline transaction + `managed_server_files` hash ownership + `install-report.json`, `server://readiness` diagnostics/crash evidence, per-command `validate_id`/reparse/realpath hardening, Adoptium SHA-256 + install lock, ZIP staging limits/atomicity, CF browser navigation/download allowlist, command newline validation, durable main-process `launcher.log`. *Intentionally deferred by doc* (and correctly absent on both sides): RCON (ADR-0011), playit.gg, schedules beyond backups, i18n, auto-update, full files editor, NSIS, Embedded-CF-browser cut-line (`docs/electron-port-plan.md:44-46,118`). *New, not a port*: the whole backups/worlds/players/metrics/content/settings surface (Rust Phase 7–9 were stubs), the HTTP/OpenAPI adapter, and `curseforge_inspect_project` key-mode.

**Systemic gaps.** (1) Validation and security policy were dropped at the IPC boundary (ids, reparse/symlink, staging, checksums, navigation), making the renderer the trust boundary. (2) Install atomicity and store atomicity regressed (in-place installs, whole-file JSON read-modify-write, no per-server uniqueness constraints, no `app.db` import). (3) Lifecycle/process identity is weaker (no command-line identity or tree kill, kill→crashed, non-blocking stop-all, unbounded start IPC). (4) Backend→renderer DTO/shape drift (pipeline report, Java candidates, CF timestamps, event payloads) is invisible to all existing backend-only gates.

**Five highest-value runtime checks for the Lead.** (1) Drive a real Modrinth and a real CurseForge install through the Create UI, then inspect step 4: the report card should throw on `pipelineReport.loader` and blank the window (bug #1) — confirm and capture the console TypeError. (2) Create a Paper server: expect failure at “installing paper” (`loader not supported: paper`, bug #7) and decide hide-vs-implement. (3) In Settings, detect Java then save the auto-selected/typed path: expect blank path and `javaPath:null` in `.app-data/app-data.json` (bugs #2/#6). (4) Start vanilla, click Console → Kill: expect status `crashed` plus crash toast (bug #3); then quit with a server running and check for an orphaned `java` PID after exit (lifecycle gap). (5) CurseForge staging: pick a ZIP, check the listed date (Invalid Date, bug #4), then re-pick a same-named ZIP and confirm it overwrites the staged file (bug #26).

## Open questions

1. Is the renderer crash in `Create.tsx:2394` reachable in the intended build? The backend-only E2E (`electron/e2e.ts`) never renders React; `--ipctest` loads the window but its “Create UI smoke” may not reach step 4. Needs a manual run of a real Modrinth/CF install in the UI.
2. Should Paper server creation be in scope? The wizard and `versions_paper` advertise it; `installLoader` has no branch (would need Paperclip/Vanilla-jar + patching or a Paper launcher download). If out of scope, the UI should hide Paper to avoid guaranteed failures.
3. Is silent port re-allocation at start (`server-process.ts:97-103`) an accepted policy change or a bug? It contradicts the rendered “Address:port” and the port-conflict UI, and Rust failed closed.
4. Was the JSON store intended to import existing `app.db` servers? Nothing in `store.ts` or `main.ts` reads `app.db`; a Tauri→Electron upgrade silently shows an empty server list.
5. What is the expected `refresh/reconcile` contract for `server.status` in the JSON store? Status is written by the process manager, but stale `running` after a hard crash is only normalized at boot (`server-process.ts:60-84`); Electron UI may show running while nothing is live if a second instance/DB edit occurs.
6. Are backups/worlds/players/metrics/content specs expected to be validated against `docs/specs/app-tabs.md` only? The Rust reference cannot adjudicate them; task-4 covers their internals.
7. Is the CurseForge embedded browser allowed to navigate/download from any host, and was the Rust allowlist (`curseforge_import.rs:2620-2627`) intentionally dropped? If not, it is a security regression.
8. Should `server_install` reject Quilt/validate input server-side (current renderer enforces), and should pipeline rejects match ADR-0005 (`Quilt` currently installable via `pipeline.ts:38`)?
