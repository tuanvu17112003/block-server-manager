# Management & content audit

Scope: the uncommitted management/content wave — `electron/services/{backups,content,metrics,players,properties,worlds,zip}.ts`, their wiring in `runtime.ts`/`ipc.ts`/`preload.ts`, renderer `src/tabs/{Backups,Worlds,Players,Metrics,Settings,Content}.tsx` + `src/store.tsx`/`src/tauri.ts` changes, and `electron/mgmt-test.ts`/`electron/ipc-test.ts`. Baseline `e3d0dbd` + working tree (in-scope sources unmodified during this audit; mtimes ≤12:17, verified). Method: full read of the above, comparison with `docs/specs/app-tabs.md` + `docs/specs/{server-installs,modpack-server-setup-overhaul}.md` + `backend-plan.md` phases 7–9 + `minecraft-technical.md` + ADR-0011, and read-only Node probes against the already-built `dist-electron` (temp data roots, stubbed `electron` module; no npm/Electron/test gates run, no app code edited). The dormant Rust `backups/worlds/players/metrics/content` modules are stubs (docs only), so `app-tabs.md` + the port plan are the spec of record. This replaces the Lead's provisional report: each provisional M finding was re-checked; corrections are listed below.

## Executive summary

- Two **P0/P1 data-integrity defects are confirmed by runtime probe and were missing from the provisional report**: a corrupt/truncated backup ZIP produces an **uncaught zlib stream error** in the shared extractor (main-process exception + a promise that never settles; 0-byte partial file), and **"backup before delete world" archives a different world than the one deleted**.
- World lifecycle is the weakest area: export→import is rejected or silently drops `world_nether`/`world_the_end`, `world_duplicate` copies only the overworld, `level.dat` is never parsed (seed unavailable/corruption invisible), and `reset` restore does not reset.
- Player features break in normal operation: `players_list` loses all online players once the 5000-line console ring fills (probe: 3.3 s, none found), and `lastSeen`/`playtime` can never work for Forge/NeoForge/Paper because the log regex only matches vanilla/Fabric format. Offline player management required by the Phase-7 spec is absent.
- Content is not a transaction: an update leaves the previous jar enabled (duplicate mod versions), the pre-update backup excludes `mods/`/`plugins/` so it cannot roll back content, required plugin dependencies never resolve, and enable/disable is allowed while the server runs.
- Settings/EULA and `server.properties` semantics are unsafe: any Settings save on a running server stops it; EULA acceptance is inferred from file existence (`eula=false` reads as accepted, probe); Java Properties escapes (`\uXXXX`, backslash) are not decoded/encoded and appended keys mix CRLF/LF.
- mgmttest is 17 happy-path checks; it never opens a produced ZIP, never restores a corrupted archive, never tests retention/scheduler/reset/rollback/import/export/player parsing/actions/content dependency paths. ipctest only invokes read commands.

## Corrections to the provisional M-01..M-16 hypotheses

- **M-06 corrected (P1→P3)**: `players_list.maxPlayers` does read the stale store value, but `Players.tsx:38-39` ignores the field and the Overview/Metrics cards use the enriched `servers_list` DTO (`store.tsx:99-107`), so there is no observed 20-vs-10 UI mismatch. It is an API-contract bug only.
- **M-03 corrected**: `maxKept` **is** clamped server-side (`backups.ts:279`); only `interval` is unvalidated. Reachability is via stale/buggy IPC or a non-shipped value, not the UI select — demoted to P2.
- **M-09 corrected (P2→P3)**: a pending world is normally active and cannot be deleted (`worlds.ts:168`); the "forever ghost" needs an out-of-band `level-name` edit. Real gaps are no cancel path and no clear-on-start.
- **M-14 corrected**: entry-count is checked before any I/O (`zip.ts:59`); writer output round-trips through the app's own extractor with correct CRC/UTF-8 (probe). Real issues are zeroed DOS timestamps, no fsync, and junction-following — P3, not a reader mismatch.
- **M-15 corrected**: manual backup/restore **do** pass `jobId` and subscribe progress (`Backups.tsx:100-106,125-133`); the real spec gaps are "shutdown-during", pre-first-run backup, and stale RCON/zoom copy.
- **M-08 corrected**: only `fs.cpSync` (`worlds.ts:153,215`) blocks the main thread; `writeZip`/`collectInputs` are async (but still unprogressed, per-file-memory).
- **M-02/M-04 demoted P1→P2** (no corruption/data loss); **M-12/M-11 confirmed P2**; **M-01/M-05/M-07/M-10/M-13/M-16 confirmed** at the stated severity.
- **New findings M-17..M-23** cover defects the provisional list omitted: corrupt-ZIP crash, world-delete backup contents, world export/import/duplicate/`level.dat`, player ring saturation, player log formats/offline management, properties escaping, restore/reset semantics.

## Findings

### M-17 · Corrupt/truncated ZIP crashes or hangs restore and world import · P0 · confirmed (probe)
- **Evidence**: `installer/core.ts:107-142`; on entry read: `:127-132` `z.openReadStream(...)` → `s.pipe(out)` with no `s.on('error')`, and the promise only settles on `write` finish or `zipfile` `error` (`:137`). `backups.ts:214` and `worlds.ts:199` call it on user-controlled archives; `main.ts` registers no `process.on('uncaughtException')`. Probe (built `dist-electron`, temp zip): flipping one deflate byte → `UNCAUGHT EXCEPTION: Z_DATA_ERROR invalid code lengths set`, extraction promise still `pending` after 4 s, 0-byte `c.txt` left in staging.
- **Symptom / root cause**: a corrupted backup (interrupted copy, disk error, truncated download) or malicious world ZIP raises an unhandled stream `error` in the main process instead of returning an error; the `:137` handler does not cover per-entry read streams. In Electron this is a main-process uncaught exception (error dialog/abnormal exit — needs runtime confirmation) or a permanently hanging `backup_restore`/`world_import` IPC.
- **Impact / fix**: app crash or frozen restore UI with partial staging data; violates the "bounded extraction / restore rollback" promise. Fix: attach `error` handlers to both streams and wrap entry pumping in try/finally with `failed=true`/`rej`; destroy the zip file; cleanup staging; validate the archive (zip EOCD) before treating it as a backup.
- **Verify**: mgmttest fixture with a truncated/corrupt ZIP → `restore_failed`/`backup-failed` (no crash, no hang, staging removed); repeat through real IPC.

### M-18 · "Backup before delete world" archives the active world, not the world being deleted · P1 · confirmed (probe)
- **Evidence**: `worlds.ts:169-171` calls `backups.create(serverId, 'before delete …', 'World-delete')`; `backups.doCreate` archives `backupNames(dir)` (`backups.ts:142`), which is `worldNames(dir)` = active `level-name` + `_nether`/`_the_end` plus `CONFIG_NAMES` (`backups.ts:42-54`) — the target `name` passed to `remove()` is never used. Probe: deleting non-active `world2` produced archive entries `world/*`, `world_nether/*`, `world_the_end/*` (active world), `server.properties`; `world2` absent, then deleted from disk.
- **Symptom / root cause**: UI toasts `"deleted after a safety backup"` (`Worlds.tsx:143`) but the deleted world is unrecoverable; the safety copy is of unrelated data. Same defect makes the "World-delete" retention class unbounded (see M-04).
- **Impact / fix**: irreversible world loss after a delete the user believes is recoverable (P1). Fix: pass an explicit input list to `create`/`writeZip` (world + dimensions + configs) or add `createForPaths(serverId, names, kind)`; label the toast accurately.
- **Verify**: mgmttest: delete a non-active world, read the produced archive with yauzl, assert `world2/level.dat` present; world_import can restore it.

### M-19 · World export→import round-trip is broken; duplicate drops dimensions; `level.dat` never parsed · P1 · confirmed (probe/code)
- **Evidence**: export includes dimensions (`worlds.ts:186` `collectInputs(dir,[world, world_nether, world_the_end])`); import (`:199-215`) recognizes only "level.dat at archive root with no folders" or "exactly one folder containing level.dat" (`:201-212`) and then `cpSync`s only that folder (`:215`). Probe: export of a world with both dimension folders produced 6 entries; re-import failed with `validation: The archive must hold level.dat at its root or in exactly one folder.` `duplicate` (`:147-160`) cpSyncs only `source` — probe left `world-copy` without `world_nether`/`world_the_end`. Discovery only tests `existsSync(level.dat)` and mtime (`:81,94`); seed/LevelName are never read, and `WorldDto` has no seed (`:16-22` ↔ `Worlds.tsx:27` hardcodes `seed:'—'`).
- **Symptom / root cause**: self-produced exports are rejected when dimension folders carry their own `level.dat` (standard modern layout; if they do not, import still copies one folder and silently loses dimension siblings). Duplicates lose nether/end; current-world card can badge the wrong world (`Worlds.tsx:78` falls back to `worlds[0]`, `:181` always renders `active`).
- **Impact / fix**: world library cannot round-trip and dimension data is destroyed by duplicate/import; seed cannot be displayed/verified; corrupt `level.dat` accepted. Fix: parse NBT `level.dat` (seed, LevelName), treat `world/ + world_nether/ + world_the_end/` as one archive unit, import all siblings under a unique base, duplicate sibling folders too, and render `active` only when true.
- **Verify**: real 1.21 survival world with generated nether/end: export → delete → import → activate → start; nether/end intact and seed matches; duplicate likewise; mgmttest importer fixtures.

### M-20 · `players_list` permanently loses online players once the console ring is full · P1 · confirmed (probe)
- **Evidence**: `players.ts:152-164` takes `baseline = processes.history(id).length`, sends `list`, then `history(id).slice(baseline)` looking for the reply; the ring is capped at 5000 (`server-process.ts:205-210`, `history()` `:54`). Probe with a 5000-line ring: `Steve` reported `online:false` after 3323 ms (poll exhaustion); with 4999 lines the same reply was found in 109 ms.
- **Symptom / root cause**: `Array.length` stops increasing at the cap, so `slice(baseline)` is always empty and every call burns the full 3 s timeout; any server past 5000 console lines shows no online players forever (metrics' `fromRing` `slice(-400)` is unaffected, so cards can disagree).
- **Impact / fix**: Players tab "online" wrong for exactly the long-running/modded servers users care about, plus 3 s IPC latency. Fix: correlate replies with a monotonic sequence counter (record `ringSeq` before sending, scan entries after that seq) or echo a unique token (`list <nonce>` is not valid; use per-command counter maintained by `onLine`); shorten timeout.
- **Verify**: mgmttest fixture ring at cap; real server after 5000+ lines → online roster correct and <500 ms.

### M-01 · Content update leaves the old jar enabled → duplicate mod versions · P1 · confirmed
- **Evidence**: `content.ts:257-262` finds `existing` by projectId and only takes a "pre-update" backup; then `:264-273` downloads to a new filename and writes meta; the old jar is never removed/disabled (no reference to `existing[0]` after the backup), so `list()` (`:116-143`) shows both enabled. The backup cannot compensate: `backups.ts:22-31` `CONFIG_NAMES` excludes `mods/`/`plugins/` (probe archive held only `world/level.dat` + `server.properties`).
- **Symptom / root cause**: installing version B of a project leaves A+B in `mods/`; duplicate mod IDs crash or load stale code, and there is no rollback path because the "pre-update" archive never contained the jar.
- **Impact / fix**: likely server crash after updating (users must find both jars manually); misleading backup. Fix: replace-by-project — move old project file(s) to `mods-disabled`/trash or delete after staging the new file downloaded to `.part`, publish atomically, keep a rollback set; or make the safety snapshot include `{active,disabled}` dirs.
- **Verify**: install A then B → `content_list` and disk contain exactly B; failure during B download leaves A intact.

### M-05 · Any Settings save on a running server silently stops it · P1 · confirmed (probe)
- **Evidence**: `Settings.tsx:284` always sends `{ name, ramMb, eulaAccepted: eula }`; `properties.ts:255-266` runs `if (typeof a.eulaAccepted === 'boolean') { if (running||starting) await stopServer(id); writeEulaFile(...) }` with no changed-check. Probe: `server_settings_update({values:{motd:'changed'}, eulaAccepted:true})` on a running DTO called `stopServer` once. Shared with F-02 in `02-frontend.md`.
- **Symptom / root cause**: editing MOTD/RAM/port on a live server disconnects players; the UI only promises a restart banner.
- **Impact / fix**: unexpected world save/stop (and possible player loss); a Save becomes a destructive action. Fix: send `eulaAccepted` only when it changed; stop only for explicit EULA revocation; other fields write + `needsRestart`.
- **Verify**: running server, change MOTD, Save → still running; change EULA → confirmation then stop.

### M-03 · Backup schedule interval is unvalidated; a bad value backs up every 60 s · P2 · confirmed (probe)
- **Evidence**: `backups.ts:273-283` casts `patch.interval` with no whitelist (`maxKept` **is** clamped at `:279`); `tick()` compares `Date.now()-last` with `INTERVAL_MS[schedule.interval]` (`:302`), which is `undefined` for unknown values → comparison false → `create(...)` on every tick (`:296-310`, 60 s `setInterval` at `:287`). Probe: schedule with `interval:'Nope'` produced 2 Auto backups in 2 immediate ticks. UI select only offers 3 values (`Backups.tsx:178-180`); auto backups emit no renderer event, so the list stays stale; backend-plan.md:86 asked for interval/cron/on-stop (on-stop absent, not marked deferred).
- **Symptom / root cause**: stale/buggy IPC client (or future UI change) turns auto-backup into a disk-filling loop; no server-side enum validation.
- **Impact / fix**: disk exhaustion and bogus backup index. Fix: whitelist `Hourly|Daily|Weekly` (reject with `validation`); emit a broadcast on auto-create and reload the tab; add/on-stop document deferral. **Verify**: `backup_schedule_set({interval:'every-second'})` → validation; valid schedule → ≤1 per interval; UI refreshes after auto.

### M-04 · Retention keeps `maxKept+1` and prunes `Pre-*` safety archives; `World-delete` is never pruned · P2 · confirmed (probe)
- **Evidence**: `backups.ts:99-113` filters out only the just-created id and `World-delete` (`:104`), then deletes `rows.slice(maxKept)` (`:105`) → regular kinds kept = `maxKept + 1`; `Pre-install` (`content.ts:260`) / `Pre-restore` (`backups.ts:209`) count toward the cap and can be deleted (probe: `maxKept=2` finished with 3 regular backups + 1 unpruned `World-delete`).
- **Symptom / root cause**: off-by-one retention; safety archives disappear exactly when a failed restore/update would need them; delete-safety archives accumulate forever.
- **Impact / fix**: weakens restore/update recovery and grows disk unboundedly. Fix: prune only `Manual`/`Auto`, keep a separate bounded safety pool (e.g. newest 2 `Pre-*`), clamp/define both counts; test mixed kinds. **Verify**: mgmttest with maxKept=2 + mixed kinds.

### M-02 · Content enable/disable is allowed while the server runs · P2 · confirmed (probe)
- **Evidence**: `content.ts:145-155` `toggle()` has no `requireIdle` (contrast `remove()` `:157-158`; `install()` `:237`); `Content.tsx:243` renders the toggle always enabled while `:170` says "Stop the server to install or remove files". Probe: `content_toggle` succeeded on a running DTO.
- **Symptom / root cause**: jar renames under a live loader can fail with Windows share/lock errors or silently apply only next start; UI gives contradictory rules.
- **Impact / fix**: half-applied mod sets and confusing errors. Fix: `requireIdle` in `toggle()` (or label "applies next restart" and block rename while running); disable button. **Verify**: running + toggle → `conflict`; stopped → moves between `mods/` and `mods-disabled/`.

### M-07 · Content install: no cancellation, meta written before dependencies, plugin deps never resolve · P2 · confirmed
- **Evidence**: `content.ts:230-304` never calls `jobs.begin()`/`isCancelled`; `:267-273` writes meta **before** dependency downloads (`:277-301`), and warnings do not roll back the primary file. Plugin-path dependencies are dead: `fetchModrinthDependency` accepts only `project_type` `undefined|'mod'` (`installer/modrinth.ts:85`) and searches `project_type:mod` (`:91`), while `content.ts:283-288` passes `loader:'paper'` for plugins → required plugin dependencies (e.g. a plugin dependency project) return `null` → warning only. No `server_side`/client-only filtering and no dedupe against `plugins-disabled/`.
- **Symptom / root cause**: progress events look cancellable but cancel is impossible; failed deps leave untracked meta and a possibly broken install; Paper plugin dependency chains can never install. Impact: partial content state and avoidable crashes; users install client-only mods onto servers.
- **Fix**: register/cancel the job, stage primary+deps then publish atomically, write meta only for published files, resolve `project_type:plugin` deps for Paper, filter version `environment.server` where available, detect disabled copies. **Verify**: cancel mid-install → no jar/meta; plugin with required dep → dep installed; client-only project rejected/skipped.

### M-08 · World duplicate/import block the main process via `cpSync`; no progress/cancel · P2 · confirmed
- **Evidence**: `worlds.ts:153,215` `fs.cpSync(...,{recursive:true})` for user world trees (hundreds of MB–GB); export runs `collectInputs`+`writeZip` (`:186`) and import/export/duplicate expose no `jobId`/progress, so the UI shows no busy state (`Worlds.tsx:125-171` fire-and-forget). Probe: duplicate of a 3-folder world copied only the overworld synchronously (see M-19).
- **Symptom / root cause**: synchronous full-tree copy on the Electron main process freezes IPC/UI for large worlds; long exports look hung; no cancel.
- **Impact / fix**: "Application not responding" during world ops. Fix: async recursive copy with `job://progress` + abort; export/import as jobs (size preflight, disallow while running) and surface progress in the tab. **Verify**: 1 GB duplicate/export stays responsive with progress and cancel.

### M-10 · "Consistent while running" backup uses a fixed 1.5 s save-off/flush wait · P2 · confirmed
- **Evidence**: `backups.ts:130-140` sends `save-off` + `save-all flush` then unconditionally sleeps 1500 ms; no console reply is parsed and `starting` is treated as live. No `Saved the game` acknowledgment; large worlds can still be writing when `readFile`s start.
- **Symptom / root cause**: partially flushed region files can enter the archive (inconsistent snapshot); commands may be ignored before the server console is ready.
- **Impact / fix**: backup restores can reintroduce chunk corruption. Fix: wait for the flush confirmation line (`Saved the game`/`Saved the world`) with a bounded timeout, cancel on stop/crash, refuse while `starting`; optionally send `save-on` twice defensively. **Verify**: chunk-heavy running server → archive taken only after flush line; backup during startup rejected/queued.

### M-11 · Settings update is not atomic: properties are written before validation · P2 · confirmed
- **Evidence**: `properties.ts:244-268`: `writePropertyValues(dir, values)` at `:246`, then name-clash (`:249-253`), RAM bounds (`:255-258`), EULA stop/write (`:260-265`), then `updateServer`; a later throw leaves `server.properties` changed while the IPC returns an error.
- **Symptom / root cause**: e.g. changing MOTD + a name that conflicts with another server persists the MOTD but reports failure; UI state and file diverge.
- **Impact / fix**: partial settings application; hidden EULA file changes. Fix: validate name/RAM/EULA first, compute DTO patch, then perform the file write + store update as one unit (rollback file on store failure). **Verify**: conflicting name + changed MOTD → validation error and `server.properties` unchanged.

### M-12 · EULA "accepted" is inferred from file existence, not `eula=true` · P2 · confirmed (probe)
- **Evidence**: `properties.ts:234` `eulaAccepted: fs.existsSync(eula.txt)`; `core.ts:494-498` writes `eula=true` only when the file is missing; `server-process.ts:95-96` trusts the JSON DTO and rewrites the missing file. Probe: `eula.txt` containing `eula=false` reported `eulaAccepted:true`. Overlaps B-20 in `01-backend-runtime.md`.
- **Symptom / root cause**: a hand-edited/false EULA shows accepted; Start proceeds and the server exits (looks like a crash), or Settings writes `true` on save.
- **Impact / fix**: EULA-gate bypass/confusion, false crash reports. Fix: parse `eula=true|false`; reconcile DB/file at start and in `server_settings_get`; refuse Start with a validation message; never overwrite `false` implicitly. **Verify**: flag true + file false → Start rejected; Settings unchecked; toggling writes/removes correctly.

### M-13 · Metrics: PowerShell-per-server every 2 s, TPS/MSPT never sampled, CPU mis-normalised · P2 · confirmed (probe/code)
- **Evidence**: `metrics.ts:46-76` spawns `powershell.exe` for every running server every 2 s (`:170-179`); `:204-208` additionally sends `list` every 15 s (console/log spam; feeds M-20 ring saturation). `fromRing` (`:119-143`) only scrapes existing log text and nothing ever sends `tps`/`mspt`, so both stay `null` unless the user types them (Paper's `/mspt` format also does not match `MSPT_REPLY` `:44` — needs runtime check). CPU is clamped to 100 (`:237`) and not divided by logical cores, so a 4-core JVM at 200 % shows 100 % (Task Manager shows 50 %). `get(id, hours)` with `NaN` yields `Date.now()-NaN` → empty samples (`:257-271`). History is rewritten synchronously every minute per server (`:106-117`) and `previous/lastBucket/history` are never cleared for stopped/deleted servers.
- **Symptom / root cause**: measurement cost/noise, permanently "—" TPS on Paper, CPU figures that cannot match Task Manager despite the Phase-9 acceptance criterion, latent range bug.
- **Impact / fix**: misleading performance data and needless process churn. Fix: one batched `Get-Process -Id a,b,c` (or persistent sample stream) at 5–10 s, active server only; normalise CPU by core count (or label as single-core %) and don't clamp; send `tps` on Paper once per interval; validate `hours` as integer 1–168; trim/clean maps on stop/delete; write history off the main thread. **Verify**: 3 servers × 10 min — CPU within ~10 % of Task Manager, no child storm, TPS present on Paper only, `hours=NaN` → validation error.

### M-21 · Player lastSeen/playtime only parse vanilla/Fabric logs; offline management missing · P2 · confirmed (probe + real log)
- **Evidence**: `players.ts:24` regex requires `[HH:MM:SS] [thread/LEVEL]: name joined…`. The real Forge 1.20.1 log in this workspace starts lines like `[26Oct2026 13:02:43.381] [Server thread/INFO] [net.minecraft.server.dedicated.DedicatedServer/]: …` (`.app-data/servers/e2e-sf5-keymode/logs/latest.log:1`), and Paper's `[HH:mm:ss LEVEL]: …` (likely; needs runtime check) also does not match — so Forge/NeoForge/Paper players always show `—`/0.0 h, and sessions before the latest.log rotation are lost (`:43-81` reads only `latest.log`, stores time-of-day only). Offline management is absent: `addOffline` requires a running server and a Mojang API call with no cache/rate-limit/429 handling (`:199-205`); the Phase-7 spec/backend plan require file edits while stopped and "Add-player works offline" (`players/mod.rs:4-7`, `backend-plan.md:80-82`); `Players.tsx:121-122` disables Add when stopped. `gamemode` is always `'—'` (`:122`) so the per-row selector (`Players.tsx:167-175`) never reflects state, and every action immediately `load()`s (`:79-84`) before the server writes its JSON (race).
- **Symptom / root cause**: roster "last/playtime" unusable for modded/Paper servers; no way to whitelist/op while stopped or when Mojang is unreachable; gamemode UI misleading.
- **Impact / fix**: half the Players tab's promise fails for the plugin/modded targets. Fix: loader-aware line matchers (regex for date-time prefix + optional logger bracket; Paper `LEVEL]`) and persist lastSeen/playtime in the store (scan rotated logs on demand or accept loss); implement direct JSON edits (whitelist/ops/banned) when stopped with restart notice; cache Mojang name→UUID and handle 429; derive gamemode from RCON/playerdata or drop the column.
- **Verify**: Forge server join/leave → lastSeen/playtime populated; stopped server → whitelist/op works on next start; gamemode reflects server value after action.

### M-22 · `server.properties` Java-escape semantics are not implemented; appends mix CRLF/LF · P2 · confirmed (probe)
- **Evidence**: `properties.ts:53-80` `parseProperties` returns values verbatim — no `\uXXXX`, `\\`, `\=`, `\:` decoding (probe: `motd=\u4F60\u597D` returns the literal escape string); `mergeProperties`/write (`:83-105,158-168`) write the UI value raw and append missing keys with `'\n'` even when the file is CRLF (probe output mixed `\r\n` lines with a final `\n` key). Vanilla Minecraft writes `server.properties` through `java.util.Properties.store`, i.e. non-ASCII is escaped and backslashes are significant.
- **Symptom / root cause**: non-ASCII/emoji MOTD typed in Settings is written raw and mis-decoded by Java; values containing `\` are reinterpreted on the next server rewrite; comments/unknown keys are otherwise preserved (verified good).
- **Impact / fix**: corrupted MOTD/seed display after save; possible value mangling. Fix: implement Properties escaping/unescaping (at least `\uXXXX`, `\\`, leading spaces) and preserve the detected EOL for appended keys; round-trip property tests. **Verify**: MOTD `你好` and `a\b` survive UI save → MC reload → Settings reload; CRLF file stays CRLF.

### M-23 · Restore: `reset` does not reset, deletions are outside rollback, no `level.dat` validation/restart · P2 · confirmed (probe/code)
- **Evidence**: `backups.ts:190-244`: extraction then swap loop; `reset` branch `:218-219` deletes an existing directory **in place** (never moved to `previous`, so the rollback list `:204,229-236` cannot restore it); only stage top-level names are touched, so current dirs not present in the archive survive. Probe: after `restore(...,'reset')`, a `world_the_end` created after the backup remained with its new `level.dat`, contradicting the UI's "wipe world dirs first" (`Backups.tsx:239`). The archive is not checked for a valid `level.dat`/backup provenance (spec: `worlds/mod.rs:4-6`, `minecraft-technical.md:8`), and the server is not restarted after restore despite the spec's stop→validate→replace→restart flow.
- **Symptom / root cause**: "reset" leaves stale dimensions/configs (mixed-world state), and a mid-swap failure after the `rm` loses data beyond rollback; a wrong/non-backup ZIP can be applied.
- **Impact / fix**: inconsistent restored servers and unrecoverable data on failure. Fix: move (`rename`) every replaced dir aside (including in reset mode), validate archive layout/level-name/`level.dat` before swapping, then swap and clean; on failure roll back all asides; optionally restart; keep `previous` for recovery when rollback is incomplete. **Verify**: reset with extra `world_the_end` → removed; forced failure mid-swap → original tree intact; wrong ZIP rejected.

### M-09 · Pending world lifecycle: no cancel, stale store entry after start · P3 · corrected
- **Evidence**: `worlds.ts:126-145` writes `level-name`/seed/type and `pendingWorlds`, returns `active:true`; only `activate()` clears (`:117-122`); server start never clears it, and `list()` re-adds the pending entry while the folder is missing (`:99-108`). A normally-created pending world is active, so delete refuses (`:168`); a ghost delete is possible only if `level-name` was changed out-of-band → `remove()` no-ops then the entry re-appears. No UI cancel path exists. Fix: clear pending on start/cancel/delete; add cancel that restores the previous `level-name`; show pending as non-actionable.

### M-14 · ZIP writer hardening: zeroed timestamps, junction-following, no fsync · P3 · corrected
- **Evidence**: `zip.ts:77-88,90-102` never write DOS time/date (probe: yauzl surfaces 1979-11-29); `collectInputs` uses `fsp.stat` on top-level names (`:40`) so a junction `config`/`world` is followed and its external files archived (probe archived outside `secret.yml`), while `walk` skips nested `Dirent` symlinks (`:22`) — inconsistent symlink defense; `writeZip` uses temp+rename (`:62,118`) but no fsync and leaves `${dest}.tmp` if the app is killed. Positive: writer output round-trips through the app extractor with correct CRC/UTF-8 (probe); entry count checked before I/O (`:59`). Fix: DOS timestamps, `lstat`/reparse rejection for top-level names, fsync + stale-temp cleanup on startup.

### M-15 · UI/spec gaps: shutdown-during, pre-first-run backup, stale RCON/zoom copy · P3 · corrected

### M-16 · Server delete leaves orphan folders, metrics files, and content metadata · P3 · confirmed (observed)
