# Installer (Modrinth/CurseForge) audit

**Scope:** `electron/services/installer/{core,modrinth,curseforge,curated}.ts`, `electron/services/installer/data/*.json`, `electron/services/pipeline.ts`, `electron/services/curseforge-staging.ts`, `electron/services/jobs.ts`, boot-time installer wiring in `electron/services/server-process.ts`, and renderer/IPC touchpoints (`src/tauri.ts`, `src/tabs/Create.tsx` read-only). Reference of record: `H:\TestAI\modrinth-curseforge\` plus the dormant Rust pipeline under `src-tauri/src/modpacks/**`. Read-only audit; no live installs, builds or API sweeps were run. Audit basis: working tree at commit `e3d0dbd` **including the uncommitted diff**; `dist-electron/` was rebuilt at 12:58 today and still contains no installer `data/` directory; `.e2e.out` is the 06:23 P3 run.

## Executive summary

- **The advertised 4-layer client-mod defense is 3-layer in every built app.** `data/*.json` (itzg 104 global excludes + force-includes, hand overrides, learned entries) are loaded from `__dirname/data`, but `build:electron` is `tsc` only — a fresh rebuild left `dist-electron/services/installer/` with four `.js` files and no `data/`. The P3 E2E masks this: it logged "168 files, 0 unsupported" and then disabled 31 already-installed client jars at first boot (`.e2e.out:3-35`); `BadOptimizations`, `betterbeds`, `BetterF3`… are in the itzg global-exclude list. Per-pack overrides can also never fire because packs are keyed by Modrinth **project id** (`Jkb29YJU`) instead of slug (`cobbleverse`, `skyfactory-5`).
- **Install can report success for a server that has never booted.** The pipeline never performs the reference/Rust mandatory `Done (` verification or launch validation (`pipeline.ts:145-191`; CF path never calls `launchCommand`). Reference `modrinth.mjs:105-139`/`curseforge.mjs:190-205` and M-10 (`specs.md:391`) require one verified start before success; E2E boots separately, so the production path is untested.
- **Cancel is a dead control.** `Jobs` owns an `AbortController` that no download, extract, fetch or installer ever consumes (`jobs.ts:11-34`, `pipeline.ts:126,140,177`). Cancelling a 576-file / ~1 GB pack lets the whole install finish and then deletes it; M-7/§16 ("300-mod install … remains cancellable") is unmet.
- **Nothing is staged or atomic.** Files are written directly into the final `<dataRoot>/servers/<id>` and rollback is a bare `rmSync` before the record delete (`pipeline.ts:132-139,193-201`). A crash/failed delete leaves a ghost server row + partial tree; there is no resume (M-4). Pack archives are also extracted without a protected-path list, so an archive-supplied `eula.txt=true` can silently accept the EULA (C-3/A-1).
- **CurseForge route A loses metadata and L3 leaks across platforms.** Prebuilt server packs produce a server row with `mcVersion: ''` (then `requiredJavaMajor('')` fails at Start) and a Java-21 guess (`curseforge.ts:104-121,191`; `pipeline.ts:88-90,133`); boot-time L3 auto-fetches Modrinth jars into **CurseForge** packs and user-modded servers (`server-process.ts:145-162`), which the reference explicitly forbids ("CF dep fetch is prune-only", `curseforge.mjs:196-198`).
- **Integrity/allowlist/reporting are partial.** Only `downloads[0]` is tried (no failover), cached mrpack/CF zips are reused without re-hash, redirects/URL hosts are never validated before executing loader JARs, optional files regress from "include by default" to "user must choose / excluded", and the preview/report DTOs omit `planId`, `target`, `sourcePin`, `schemaVersion` — while the UI claims the full report is saved as `install-report.json`, which is never written.

## Findings

Severity: **P0** release-blocking correctness/legal · **P1** high-impact functional/security divergence · **P2** partial/migration/UX-contract defect · **P3** hardening/robustness. Confidence: *confirmed* (code + local evidence), *likely* (static reasoning, runtime-dependent), *needs runtime check*.

### INST-001 — Curated L4 data is absent from every built app; per-pack keys can never match — **P0, confirmed**
- **Evidence:** `electron/services/installer/curated.ts:23-26` (data dir = `path.join(__dirname,'data')`); `package.json:12` (`build:electron` is `tsc` only) + `package.json:7` (main = `dist-electron/main.js`); `electron/tsconfig.json:7` (outDir `../dist-electron`). Observed: `dist-electron/services/installer/` contains only `core.js/curated.js/curseforge.js/modrinth.js` after the 12:58 rebuild; no `data/`. Runtime consequence: `.e2e.out:3` "COBBLEVERSE: 168 files, 0 optional, 0 unsupported" followed by `.e2e.out:4-35` L2 disabling `BadOptimizations`, `betterbeds`, `BetterF3`… — all in `electron/services/installer/data/itzg-modrinth-exclude-include.json` globalExcludes. `.app-data` sidecar for Prominence II Fabric shows 565 index paths / 368 installed jars vs the reference's 341 (`sample/modpack-install-results.md:33-35`). Pack-key mismatch: `modrinth.ts:61` sets `slug = ref.projectId`; `pipeline.ts:69` and `modrinth.ts:142` pass it as `packSlug`; itzg `modpacks` keys are slugs (`cobbleverse`, `skyfactory-5`, …, cf JSON), never project IDs.
- **Symptom:** installs contain all client mods, first Start spends ~34 s disabling 31 jars, community force-includes (`simplytooltips`, `s-lib`) cannot protect required server libraries, installed/skipped counts are wrong, learned data has no effect.
- **Root cause:** source tree is the data root instead of packaged resources; no copy/asset step; runtime pack identity is a project id, not the curated slug.
- **Impact:** the migration's headline capability (4-layer defense) silently degrades to L1 metadata + boot L2/L3; avoidable crash loops and wrong "complete" reports; E2E gives false confidence.
- **Fix:** ship JSON as Electron resources (`extraResources` or generated module) and resolve via `app.isPackaged ? process.resourcesPath : app.getAppPath()`; add a build step that fails if data is missing; carry a real slug (add `slug` to `ModrinthModpackDto`/search mapping, resolve `/project/{id}` when needed) and store it in the sidecar; map CF slugs from the official API for staged route A too.
- **Verification:** rebuild → assert `dist-electron/.../data` exists; install Cobbleverse and assert `skippedUnsupported > 0` with all itzg global excludes absent from `mods/`; install a Prominence II Fabric version and compare installed count to reference (341).

### INST-002 — Install reports `complete` without verify-start or launch validation (M-10) — **P0, confirmed**
- **Evidence:** `electron/services/pipeline.ts:145-188` (engine call → publish → `status:'complete'`, no start); `electron/services/installer/modrinth.ts:163` only computes `launchCommand`; `electron/services/installer/curseforge.ts:215-235` never calls `launchCommand`; reference `sample/modrinth.mjs:105-139` and `sample/curseforge.mjs:190-205` run `startWithAutoFix` before writing the sidecar/returning; `specs.md:391` M-10; E2E boots separately (`electron/e2e.ts:62-71,86`), so the pipeline path itself is never verified.
- **Symptom:** "Modpack server installed and saved" toast followed by a Start failure (missing loader artifact, client-mod crash, wrong Java) on the console tab.
- **Root cause:** the port kept the spike's `startWithAutoFix`/`startAndVerify` helpers only for the E2E path; the pipeline never wires them (comment `pipeline.ts:1-2` claims rollback+sidecar only; `docs/electron-port-plan.md:62` cites boot L2/L3 instead of install verification).
- **Impact:** success is not a trustworthy state; failed packs look installed, wasted GBs; launch artifacts are never validated before publication (the Rust pipeline re-resolves and validates the plan, then publishes only through `transaction::publish_new_staged_install`; `commands.rs:681-702,784`).
- **Fix:** after download+overrides, resolve `launchCommand`, validate loader completeness, and run a bounded `Done (` start (kill/`stop`) or an explicit user opt-out; include "verified/unverified" in the report and require verified or `awaiting-eula` for `complete`.
- **Verification:** install a pack whose `mods/` was deliberately broken (or remove `run.bat`) → pipeline must fail/needs-attention instead of `complete`; install Cobbleverse through the UI path and observe one `Done (` during install.

### INST-003 — Cancellation cannot interrupt the installer — **P1, confirmed**
- **Evidence:** `electron/services/jobs.ts:11-34` creates/aborts an `AbortController`, but no installer function accepts a signal (`core.ts:27-62` fetch/download, `core.ts:213-226` runInstaller, `core.ts:107-142` extractZip); the pipeline only polls at boundaries: `pipeline.ts:126,140,177`; the renderer wires Cancel at `src/tabs/Create.tsx:1307-1338,2459`; Rust checks cancellation throughout (`src-tauri/src/modpacks/pipeline/commands.rs:661,704,757`; `JobControl`).
- **Symptom:** clicking Cancel during a 168-file/576-file install leaves the progress screen running for minutes, then reports "cancelled" after deleting the fully-built tree.
- **Root cause:** job registry was ported as a flag store; engine port has no cancellation plumbing; loader child processes are not killed.
- **Impact:** dead control (anti-goal A-5), multi-GB wasted downloads, no resume; a cancel arriving during publication is ignored (check only at line 177), so the app can report `complete` after the user cancelled.
- **Fix:** thread `AbortSignal` through `fetchOk/download/extractZip/runInstaller`, check per file/stage, kill child installers on abort, make publication a single non-cancellable phase with a clear "publishing" state, keep rollback complete-or-nothing.
- **Verification:** cancel Prominence II Fabric (341 files) 10 s in and assert install stops within seconds, staging removed, result `cancelled`, no record; repeat during CF SF5 key-mode download.

### INST-004 — Non-transactional install into the final directory; rollback is fragile — **P1, confirmed**
- **Evidence:** `electron/services/pipeline.ts:132-139` creates the store row before any download, `pipeline.ts:138,194-201` installs directly into `<dataRoot>/servers/<id>` and rollback is `fs.rmSync` then `store.deleteServer` with no try/catch or journal; engines write into `dir` directly (`modrinth.ts:136-137`, `curseforge.ts:170,194`); plan promised "staged download w/ hashes → transactional publish" (`.zcode/plans/plan-session_*.md:40`), reference design requires staging+swap (`modpack-install-design.md:94-96`), Rust uses `create_pipeline_staging` + `transaction::publish_new_staged_install` (`commands.rs:706,784`).
- **Symptom:** app kill/power loss mid-install leaves a partial server folder plus a persisted server row; if `rmSync` fails (open `.part` handle on Windows, permissions) the record delete never runs and the IPC returns an internal error; no resume after failure (M-4).
- **Root cause:** spike CLI wrote directly and called it "throwaway"; the app pipeline copied that shape instead of the Rust staging transaction.
- **Impact:** ghost/broken servers, disk leaks, misleading errors, no recovery path; "complete-or-rolled-back" (M-7) only holds when everything behaves.
- **Fix:** install into `<dataRoot>/installer-staging/<jobId>`, write plan/report/management snapshot there, publish via rename in one commit point, then insert/update the record (record id pre-generated); cleanup in `finally` with retries and a startup "orphaned staging" sweep.
- **Verification:** hard-kill the app mid-download, restart, assert no ghost record/partial final dir and staging is reclaimed; simulate an EBUSY rollback.

### INST-005 — Archive content can accept the EULA / overwrite protected manager paths — **P1, confirmed**
- **Evidence:** `electron/services/installer/modrinth.ts:156-161` extracts `overrides/` with `skipExisting:true` and no deny list; `electron/services/installer/curseforge.ts:196-201` extracts the **whole root** for route A packs; `electron/services/pipeline.ts:181` only writes `eula.txt` when the user checked the box, but a pack-supplied `eula.txt=true` already exists so nothing gates it; `core.ts:494-498` `writeEula` is existence-gated, `core.ts:499-504` `ensureServerProperties` leaves pack `server-port` untouched. Contract: `docs/specs/modpack-server-setup-overhaul.md:31` protects `world/`, `eula.txt`, `logs/`, `backups/`, manager artifacts; `docs/specs/curseforge-server-pack-import.md:113` "Preserve EULA"; `specs.md:525` C-3 / anti-goal A-1.
- **Symptom:** installing a server pack that ships `eula.txt` (or a Modrinth pack with `overrides/eula.txt`) records `eulaAccepted:false` while the file says `eula=true`; server may be startable without consent; pack `server.properties` can pin a port/values the manager believes it set; pack `world/` content appears without review.
- **Root cause:** the spike deliberately auto-accepted EULA and had no protected-path filter (`sample/core.mjs:329-338`); only the consent write was ported, not the reserved-path enforcement the Rust pipeline added.
- **Impact:** legal/contract violation (explicit EULA consent), manager/runtime values silently overridden; conflicts with the app's anti-goals.
- **Fix:** add a shared extraction deny-list (EULA, world/logs/backups, manager files, launch scripts) that applies to every layer before writes; write `eula.txt` exclusively from consent; merge only manager-owned `server.properties` keys and record what was skipped.
- **Verification:** synthetic route-A ZIP containing `eula.txt=true` + `server.properties(server-port=9999)`; install with EULA unchecked → no `eula=true`, port matches the wizard; same via `overrides/`.

### INST-006 — CurseForge route A prebuilt packs install with blank MC/loader metadata and a guessed Java — **P1, confirmed**
- **Evidence:** `electron/services/installer/curseforge.ts:103-121` classifies a prebuilt pack with `minecraftVersion: null` and only a loader-name guess; `pipeline.ts:88-90` turns that into `loader {kind:'forge', minecraftVersion:''}`; `pipeline.ts:133` persists `mcVersion:''`; `curseforge.ts:191` picks Java 21 when `mc` is unknown; `runtime.ts:46-51` later calls `requiredJavaMajor(dto.mcVersion)`, which throws for `''` (`core.ts:157-158`); Rust requires consistent exact metadata + revalidation (`docs/specs/server-pack-install-correctness.md:48-53`, ADR-0013) and validates exact Java (`commands.rs:644-660`).
- **Symptom:** a complete (prebuilt) author server pack installs "successfully" with an empty Minecraft version; Start fails with `cannot map java major for non-1.x MC version ""`; 1.12.2/1.18.2 packs get Java 21 downloaded and an `UnsupportedClassVersionError`; the server card shows blank MC.
- **Root cause:** the port kept the spike's narrow route-A detection (only prebuilt-branch names get a version, from a shipped installer JAR name) and never implemented the Rust launch/args/library metadata inference.
- **Impact:** the primary keyless CF "server pack" route can produce servers that never start; wrong JDK downloads; broken catalogue metadata.
- **Fix:** infer MC/loader/build from `libraries/net/minecraftforge|neoforged/...`, `win_args.txt`/`user_jvm_args.txt`, `fabric-server-launch.jar` manifest, or installer JAR coordinates; fail preview closed when they disagree or are absent; carry the resolved pin into `createServer` and re-validate at install.
- **Verification:** import a prebuilt Forge server pack (e.g. Craft to Exile 2 / RLCraft-style complete archive) and confirm the preview shows MC+loader, the row stores them, and Start reaches `Done (` with the correct Java.

### INST-007 — L3 dependency injection runs for CurseForge and every server start — **P1, confirmed**
- **Evidence:** `electron/services/server-process.ts:145-162` calls `fetchModrinthDependency` for every crash attribution without consulting the sidecar platform (only L2 uses the sidecar, line 110-114); `modrinth.ts:75-110` resolves project-id/slug and installs a Modrinth file; reference is explicitly Modrinth-only: `sample/curseforge.mjs:196-198` "CF dep fetch is prune-only … keyless search is blocked", results `modpack-install-results.md:121`; hardened Rust policy says no recursive fetch and no silent override (`docs/architecture/adr/0015-*.md:14-18`; `docs/specs/modpack-server-setup-overhaul.md:37-38`).
- **Symptom:** a CF pack that reports a missing dependency silently gains a Modrinth jar of the same mod id; arbitrary user servers (including standalone Forge/Purpur installs) can be modified on boot.
- **Root cause:** boot loop was ported from the spike's Modrinth `fetchDep` without the reference's platform gate nor Rust's "diagnose, never repair" policy.
- **Impact:** cross-platform mod injection (wrong project/version/licence, CurseForge redistribution rules bypassed), pack corruption, hard-to-diagnose servers; diverges from both the reference and the dormant implementation.
- **Fix:** gate L3 fetch to `sidecar.platform === 'modrinth'` (or remove auto-fetch entirely and surface the missing-dependency diagnostic + manual list as ADR-0015 requires); never inject into CF or non-modpack servers.
- **Verification:** remove one dependency jar from a CF pack and Start → no new file appears in `mods/`; start a standalone Forge server with a missing-dep crash → diagnosis only, files unchanged.

### INST-008 — `appendLearned` writes into the app directory; first L3 disable crashes Start — **P1, confirmed**
- **Evidence:** `electron/services/installer/curated.ts:59-66` writes `path.join(__dirname,'data','env-overrides-learned.json')`; `electron/services/server-process.ts:143` calls it unguarded inside `start()`; the path does not exist after a build (INST-001), and a packaged app would write into `app.asar`/Program Files; the data file is git-tracked (`git ls-files` shows it), so dev runs dirty the working tree.
- **Symptom:** first crash that disables a jar throws `ENOENT …env-overrides-learned.json` (or `EACCES` when packaged), so `server_start` rejects before the L3 retry round; jars already renamed into `mods-disabled/`; the learned defense never accumulates in production.
- **Root cause:** spike wrote next to the module; the app port didn't move mutable state into the data root.
- **Impact:** auto-fix breaks exactly when needed; misleading internal error; global learned file polluted by any user's crash (substring `match` applied to all future installs).
- **Fix:** persist learned entries under `<dataRoot>/installer/learned.json`, merge in `makeCuratedResolver`, wrap writes in try/catch, scope entries to platform/pack and cap growth.
- **Verification:** install a pack with a crashing client mod; assert no ENOENT, learned JSON created under data root, and the retry proceeds.

### INST-009 — Optional-file policy regressed from "include by default" to "user must choose / skipped" — **P1, confirmed**
- **Evidence:** `modrinth.ts:145-150` skips every `env.server=optional` unless the UI choice says include; `pipeline.ts:70-76` emits `action:'awaitingUserChoice', reason:'userChoice'` for optional; the contract reserves `optionalDefaultKeep` (`src/tauri.ts:303-318`) and the UI only preselects that reason (`src/tabs/Create.tsx:911-917`) while treating `awaitingUserChoice` as a conflict that blocks install (`Create.tsx:1015-1021,1409-1416`) with "conflicting client/server declarations" copy (`Create.tsx:2011-2018`); required contract: optional included by default (`docs/specs/server-pack-install-correctness.md:26`, ADR-0013) with visible choices; Rust re-derives decisions and rejects unresolved `AwaitingUserChoice` only for real conflicts (`commands.rs:688-702`).
- **Symptom:** preview shows N "choices to review" as radio conflicts; install is blocked until every optional file is answered; if the API is called programmatically with empty choices, optional server mods are silently omitted.
- **Root cause:** preview mapping conflated "optional default keep" with "conflicting signals"; install path has no default-include.
- **Impact:** broken UX for packs with optional server content, unnecessary exclusions, contract/type drift (no `conflictingSignals` ever produced either).
- **Fix:** emit `reason:'optionalDefaultKeep'` + `action:'include'` for optional (default include), reserve `awaitingUserChoice` for contradictory signals, and make `installModrinth` include optional unless the user explicitly excluded; add the missing conflict detection.
- **Verification:** preview a pack with ≥1 optional file → checkboxes pre-checked, Install enabled immediately; install and confirm optional jars exist.

### INST-010 — No source failover, no cached-file re-verification, one failure kills the whole install — **P1, confirmed**
- **Evidence:** `modrinth.ts:151` uses only `f.downloads[0]`; `core.ts:42-62` never sends `Range`, retries nothing at the download layer, and `fetchOk` (`core.ts:27-37`) retries only network/5xx without `Retry-After`/429; existing cache is trusted: `modrinth.ts:64-65` skips download if the mrpack exists, `curseforge.ts:150-151,166-167` skip if the CF zip exists (no hash/self-hash re-check); a single failed Modrinth file aborts the run (no try/catch in `modrinth.ts:144-154`) and rollback deletes everything, whereas reference collects `failed[]` and continues (`sample/modrinth.mjs:77-91`); contract: source failover, 3 attempts, SHA-1+SHA-512 before placement (`docs/implementation/modpack-download-source-failover.md:5-18`), self-SHA256 persisted/re-verified for keyless CF (`specs.md:202-204`), M-4 manual list/resumable (`specs.md:385`).
- **Symptom:** transient CDN error loses the whole multi-GB install; a truncated/poisoned cache file makes future installs fail forever; 429 responses surface as crashes; no manual-required list for Modrinth.
- **Root cause:** minimal spike downloader was ported literally; later Rust reliability work (candidate rotation, hash re-verify, worker pool) not ported.
- **Impact:** low reliability for the exact scenario (large packs) the feature targets; silent acceptance of stale bytes; no actionable failure evidence.
- **Fix:** implement ordered candidate rotation with 3 attempts/backoff/Retry-After; persist a per-file hash ledger (marker + computed SHA-256) and verify on reuse; convert per-file failure to a reported `failed/manuallyRequired` list with policy (abort only when required+policy says so); add Range resume for non-`www.curseforge.com` hosts.
- **Verification:** corrupt a cached `.mrpack` and reinstall → re-download or hash error, never silent success; request a pack whose primary URL 404s but secondary works → install succeeds; 300-mod cancellation/progress run.

### INST-011 — No HTTPS host allowlist or redirect validation before executing downloads/loader JARs — **P1, confirmed**
- **Evidence:** `core.ts:32` uses `redirect:'follow'` with no per-hop check; `core.ts:42-46` downloads arbitrary URLs from a pack manifest; `core.ts:227-278` fetches and **executes** Forge/NeoForge/Fabric loader installers from followed redirects; `ensureJava` (`core.ts:192-209`) and entity metadata likewise; contract requires explicit per-hop allowlists/cap (`docs/specs/modpack-server-setup-overhaul.md:27-29`; `docs/implementation/modpack-download-source-failover.md:9`; ADR-0018:9-11).
- **Symptom:** a local or edited `.mrpack` with `downloads[0]="https://127.0.0.1:.../x.jar"` (or an API/redirect compromise) makes the app fetch and run attacker-controlled content with server-install trust; no host/HTTPS diagnostics.
- **Root cause:** spike assumed trusted manifests; the port never added the URL policy the Rust pipeline gained.
- **Impact:** SSRF into the local network and drive-by installer execution are feasible from a user-supplied archive — the highest-impact security gap in the installer.
- **Fix:** central `assertAllowedUrl(url, provider)` enforcing HTTPS, provider host allowlists, max 3 redirects validated manually (`redirect:'manual'`), applied to every download (packs, loader metadata/artifacts, Adoptium, CF CDN, dependency fetch); refuse to execute any artifact fetched through an unapproved redirect.
- **Verification:** synthetic `.mrpack` with a `file://`/localhost/mismatched-host download URL → fail closed with a typed error; loader URL redirected to an unlisted host → no execution.

### INST-012 — CF staging is racy, leaks listeners, and exposes partial/arbitrary files — **P2, confirmed (one hunt item needs runtime check)**
- **Evidence:** `electron/services/curseforge-staging.ts:28-41` attaches a new `session.on('will-download')` every `openBrowser()` and never removes it on close (line 42) — the session partition is shared, so reopen adds duplicate handlers; `line 30-31` sets the **final** save path, so `listZips` (`51-58`) can list a growing/partial `.zip`; `line 29` id = basename+`Date.now()` collides for same-name downloads; `60-68` uses blocking `copyFileSync` to a non-unique destination (silent overwrite, no cancel/progress); `83-88` joins an unvalidated renderer-provided `name` (path traversal read/install of arbitrary local zips); no navigation/host allowlist (reference ADR-0012 and `docs/specs/curseforge-server-pack-import.md:38-53,105-113` require CF+forgecdn-only navigation, completion-confirmed staging, partial-file hiding, unique names).
- **Symptom:** partial/corrupt ZIPs selectable and classified "unreadable"; reopening the embedded browser fires duplicate `curseforge://download` events; duplicating a 1 GB external ZIP freezes the UI; a compromised renderer can inspect/extract any local ZIP; any page-initiated download lands in managed staging.
- **Root cause:** route C was implemented as the minimum Electron `will-download` capture; the Rust staging lifecycle (completion gating, native cancel, allowlist) wasn't ported.
- **Impact:** wrong inputs installed, races with the download itself, main-process stalls, renderer→filesystem boundary weakened.
- **Fix:** save to `<name>.partial`, on `done(completed)` verify ZIP magic + atomically rename, list only completed names; unique suffix/overwrite confirmation; async copy with cancel/progress; `removeListener` on `closed`; navigation allowlist (`curseforge.com`, `forgecdn.net` true subdomains); validate `zipName` ∈ `listZips()` and containment; dedupe by item id.
- **Verification:** open/close/reopen the browser then download twice → exactly one update stream per transfer; inspect while downloading → not listed; try `curseforge_inspect_zip` with `..\..\x.zip` → rejected.

### INST-013 — Preview/install state is unbound, unbounded, and never revalidated — **P2, confirmed**
- **Evidence:** `pipeline.ts:24-32,41` holds previews in a plain in-memory map with no TTL/cap; `pipeline.ts:56-107` freezes decisions but `previewInner` never snapshots source bytes; `pipeline.ts:209-214` returns the raw local file path (no copy/size cap) and `219` makes `release_local_mrpack` a no-op; install consumes `held.index` and re-reads the mrpack only for overrides (`modrinth.ts:157`), so a replaced/edited archive is installed against the old plan; a CF project's "latest file" can change between preview and install (`curseforge.ts:140-155`); `resolveMrpack` never verifies project↔version ownership (`modrinth.ts:55-69`); Rust has TTL/max sessions (`commands.rs:41-43`), snapshot+size cap (`201-230`), re-resolve/reject plan drift (`681-702`), and preview removal on `release_local_mrpack` (`1284-1305`).
- **Symptom:** reviewed decisions don't match installed bytes; local `.mrpack` deleted/moved between preview and install → obscure failure; stale previews leak memory; duplicate job ids overwrite the registry.
- **Root cause:** preview was modeled as "resolve once, install from RAM"; the Rust "exact pin + archive fingerprint" invariant (ADR-0017) wasn't ported.
- **Impact:** correctness/audit gap for the review step, tamper window between preview and install, memory leak in long sessions.
- **Fix:** copy local mrpack into a managed snapshot (bounded), hash it, store fingerprint in the preview; re-resolve remote pins at install and reject drift; expire previews (TTL/max) and delete snapshots on release; reject duplicate active job ids.
- **Verification:** swap the cached mrpack between preview and install → install must fail with "plan changed"; wait 30+ min then install → preview expired.

### INST-014 — Report/plan DTO and sidecar contract incomplete; UI claim is false — **P2, confirmed**
- **Evidence:** `pipeline.ts:125` builds a minimal report (`status/stages/files/warnings/errors`), `152-155,164-169` store counts as fake "file path" rows, `203-205` writes only `msm-install.json` (`platform/slug/files/loader/mc/at`); nothing writes `install-report.json`, `install-plan.json`, `managed-files.json`, `launch-config.json` (grep: no writer in `electron/`), while `src/tabs/Create.tsx:2396` renders `report.planId` (undefined) and `:2439` claims "The complete report is saved in install-report.json"; contract DTOs (`src/tauri.ts:320-334,392-404`) require `schemaVersion/planId/createdAt/target/sourcePin/loader/file decisions/hashes`; Rust writes all four artifacts (`report.rs:11-14`, `commands.rs:671-680,784`), reference writes a full sidecar (`sample/modrinth.mjs:100-104`, `sample/curseforge.mjs:189-191`), M-8 requires provider/project/version recording (`specs.md:389`).
- **Symptom:** report panel always says "report undefined"; file outcomes are counts, not paths/hashes/hosts; no install-plan/source pin/lock evidence on disk; remote versionId is not recorded, CF sidecar `files: []`.
- **Root cause:** DTO mapping was simplified to whatever the renderer tolerated; Rust report/plan/ownership artifacts were treated as non-goals without documenting the cut.
- **Impact:** no reproducible/auditable install record, no future update/ownership diffing, UI shows untruthful information; acceptance criteria for the overhaul pipeline met only superficially.
- **Fix:** construct real `PipelineInstallPlan`/`Report` DTOs (planId/target/sourcePin/loader evidence/per-file hashes+outcomes/stages), write the four JSON artifacts in staging before publication, include provider project/version/file IDs in the sidecar, and stop telling the user a report exists until it does.
- **Verification:** install a pack; assert artifacts exist and UI shows planId; compare sidecar to M-8 fields.

### INST-015 — Override handling misses `server-overrides/`, re-adds user-excluded mods, and has no protected paths — **P2, confirmed**
- **Evidence:** `modrinth.ts:156-161` extracts only `root:'overrides/'`; `excludeFn` only excludes files whose curated verdict is `unsupported` — it ignores `env.server:'unsupported'` declared files and the user's `exclude` choices, so a jar chosen "Exclude" in the wizard can be re-added from `overrides/mods/`; `curseforge.ts:199-201` similarly extracts `overrides/` only; contract requires shared then `server-overrides/`, never `client-overrides/` (`docs/specs/modrinth-overrides.md:3-9`, `docs/specs/server-pack-install-correctness.md:31`), and protected-path checks (INST-005). Reference spike handled only `overrides/`; Rust handles both layers.
- **Symptom:** packs whose server tweaks live in `server-overrides/` lose them; a user-excluded optional jar silently reappears; manager/pack values conflict with protected paths.
- **Root cause:** spike-era override extraction was ported verbatim without the later Rust override spec.
- **Impact:** wrong file set on server (both under- and over-inclusion), user intent ignored, harder-to-diagnose pack behavior.
- **Fix:** extract `overrides/` then `server-overrides/` (skip `client-overrides/`), apply the shared protected-path deny list, and exclude any path whose decision/choice is `exclude`/`unsupported` regardless of layer.
- **Verification:** fixture mrpack with a shared override, a server override, an optional jar excluded by the user, and a client override → only shared+server applied, optional jar absent, client override absent.

### INST-016 — Boot-time L2 scans/mutates every server on every Start — **P2, confirmed**
- **Evidence:** `server-process.ts:109-114` runs `applyJarSideness` on every start for every server (curated can be `null`, so no protection) before spawning; `core.ts:476-490` renames jars into `mods-disabled/`; `.e2e.out:3-35` shows the scan starting at 23:20:53 and the last jar move at 23:21:27 (~34 s) before boot; no `server://` event or DTO change reports the disabled jars (main-process `log()` only); reference ran L2 once during install before the verified start (`sample/modrinth.mjs:107-108`), Rust validates pre-publication.
- **Symptom:** every Start of a large pack is delayed ~30-60 s with the UI stuck on "starting"; jars disappear from `mods/` without explanation; repeated scans every start; user servers are mutated too.
- **Root cause:** L2 was moved from install to boot to keep the pipeline simple, without persisting verdicts or surfacing effects.
- **Impact:** perceived hangs, lost user intent, wasted I/O; first-start failures become harder to attribute (was it L2 or L3?).
- **Fix:** run the jar scan once at install/publish (persist verdicts + protect set in the sidecar/report) or at least cache per-hash verdicts and emit a status/log event; restrict to sidecar-backed modpack servers.
- **Verification:** measure Start latency before/after for a 168-jar pack; assert a `server://status` or log notice lists disabled jars.

### INST-017 — Loader/launch coverage gaps vs reference and Rust — **P2, confirmed**
- **Evidence:** `core.ts:300-315` `launchCommand` only understands `run.bat`, `fabric/quilt-server-launch.jar`, a root `forge-*.jar`, and `server.jar` — no `win_args.txt`/`user_jvm_args.txt` parsing, no `launch-config.json`, no `-DignoreList` handling (Rust `docs/specs/server-pack-install-correctness.md:15-21,50-53`; ADR-0018); `curseforge.ts:205` only treats `run.bat`/`libraries/` as prebuilt, while the reference also accepts `fabric/quilt-server-launch*.jar` (`sample/curseforge.mjs:140-163`), so a prebuilt Fabric/Quilt pack without `run.bat`/`libraries` throws; no Fabric `depends.java` preflight (ADR-0014) and no pre-publication missing-hard-dependency block (ADR-0015) before `pipeline.ts` publishes; no Quilt rejection in the pipeline (Rust `commands.rs:636-641`), only UI gating (`Create.tsx:298,1990-1993`); loader artifacts downloaded into `cacheDir` are reused without checksum checks (`core.ts:245,254,270`).
- **Symptom:** valid prebuilt Fabric/Quilt server packs fail "server pack has neither a loader nor a manifest"; packs requiring a newer Java or missing hard deps install then crash; IPC callers can install Quilt; tampered cached installer jars execute.
- **Root cause:** spike launch/detection logic ported; later Rust loader/launch/validation work was not.
- **Impact:** avoidable install failures and post-publication crashes; policy (Quilt removal) enforced only in the renderer.
- **Fix:** port loader completeness + launch parsing (`win_args/user_jvm_args`, ignoreList), validate launch mode before publish, add Fabric Java/dependency preflight and missing-dep block, reject Quilt server-side, verify cached installer hashes.
- **Verification:** import a prebuilt Fabric server pack (e.g. Prominence II server ZIP) → installs + starts; install a pack with a known missing dep → blocked with named mods; call `modpack_pipeline_install` for a Quilt preview → validation error.

### INST-018 — CurseForge route B validation/reporting gaps — **P2, confirmed**
- **Evidence:** `curseforge.ts:177-183` parses `manifest.json` without checking `manifestType`/`manifestVersion` (reference validates both: `sample/curseforge.mjs:63-71`); `218-231` never cross-checks file `gameVersions` against the pack's MC/loader (only "Client without Server" skip) and silently drops `required:false` optional files without surfacing counts; `manuallyRequired` page URL is a generic search (`curseforge.ts:229`); no self-hash persistence (INST-010); the newly-enabled route B (`pipeline.ts:82-87`, uncommitted) has no E2E coverage (`e2e.ts:74-94` exercises only engine route A).
- **Symptom:** any ZIP with an arbitrary `manifest.json` is treated as a CF client pack; files for the wrong MC/loader can be downloaded; skipped optional mods vanish silently; expected `manuallyRequired` panel becomes generic warnings.
- **Root cause:** route B came from the spike's minimal path; the Rust policy layer and SPEC route-B rules (`modpacks.md:60-69`) were not ported.
- **Impact:** brittle/wrong installs for the keyless client-pack route; A-2/D-24 partially unmet.
- **Fix:** validate the manifest schema, filter client-only + MC/loader-mismatched files, persist self-hashes, report skipped optional/manual files with real project URLs, add a fixture + E2E for route B.
- **Verification:** fixture manifest with wrong `manifestType` → rejected; DawnCraft client pack route B → expected mod set and manual list visible.

### INST-019 — Archive hardening and limits are incomplete — **P3, confirmed**
- **Evidence:** `core.ts:107-142` enforces only an uncompressed `maxTotalBytes` (2 GiB) — no compressed-size cap, entry count, free-space preflight, duplicate-normalized-path rejection, symlink/reparse rejection, or Win32 reserved-device-name rejection (`safeTarget` 68-75 only blocks absolute/`..`); errors are plain `Error` strings, not the typed codes in `specs.md:463-474`; `extractZip` leaves partially written files if a later entry fails (cleaned only via whole-dir rollback).
- **Symptom:** large/crafted archives can fill the disk or fail obscurely; reserved names (`CON`, `NUL`) fail mid-extraction; path-safety test matrix from the spec is unmet.
- **Root cause:** minimal spike extractor ported as-is.
- **Impact:** DoS/disk exhaustion and confusing failures; spec acceptance gaps.
- **Fix:** port Rust limits (2 GiB compressed / 100k entries / 20 GiB expanded / free-space + 512 MiB headroom), reserved names, duplicate paths, symlink entries, and map errors to typed codes.
- **Verification:** crafted fixture per path/limit; assert typed errors and no partial publication.

### INST-020 — Progress/stage fidelity misses the contract — **P3, confirmed**
- **Evidence:** no byte callbacks exist in `core.ts:42-62`/`extractZip`; Modrinth progress only every 25 files by count (`modrinth.ts:153`); `jobs.ts:3` exposes `bytesDownloaded/bytesTotal` but nothing emits them (UI reads them, `Create.tsx:955-958`); report stages are 2–3 ad-hoc strings (`pipeline.ts:156,168,183`) instead of the ordered stage model in `src/tauri.ts:392-404`/Rust report; §16 requires per-file progress for a 300-mod pack (`specs.md:439`).
- **Symptom:** progress bar jumps 5→…→95 with no bytes/ETA; stage list in the report is uninformative.
- **Root cause:** the spike downloader only logged counts; the port kept that contract while the IPC/job DTO already promised byte progress, and the pipeline report writer was simplified to counts.
- **Impact:** users cannot estimate remaining time on multi-GB packs; the UI silently shows empty byte fields; §16 performance/acceptance budget is unmet.
- **Fix:** streaming byte callback in `download()`, per-file job events, stage enum with ordered outcomes.
- **Verification:** install a 300+ file pack and observe monotonic byte progress; compare stage list to spec.

### INST-021 — API/error/DTO robustness gaps — **P3, confirmed (one API assumption needs runtime check)**
- **Evidence:** `modrinth.ts:17,32` and `curseforge.ts:29,161` call raw `fetch` without `res.ok` checks (a 429/5xx HTML/JSON body reaches `.json()` then `j.hits.map` → `TypeError`); `curseforge.ts:19-25` official calls have no retry/backoff; `cfKey` caches the key forever (`curseforge.ts:12-17`) and there is no in-app key UI (only `<dataRoot>/curseforge-key.txt`); `inspectCurseForgeProject` (`curseforge.ts:59-85`) relies on the official `slug` search parameter and selects `files[0]` regardless of release type (assumption needs runtime check); errors are plain `Error` with no `code`, contradicting `specs.md:463-483`.
- **Symptom:** opaque `Cannot read properties of undefined` errors on provider outages; key changes require app restart; mismatched latest-file selection for key mode.
- **Root cause:** the spike used bare `fetch().json()` chains and plain `throw new Error`; the port did not adopt the Rust error-code/transport layer (`specs.md:19` D-17).
- **Impact:** users get unactionable errors during outages/rate limits; key-mode configuration is undiscoverable or stale until restart; hidden coupling to an undocumented search parameter.
- **Fix:** route all calls through `fetchOk`, map to typed error codes, add key settings (safeStorage) + cache invalidation, select release/latest matching MC+loader.
- **Verification:** stub 429 → readable typed error; change key file at runtime → picked up without restart.

### INST-022 — E2E covers the engine, not the production pipeline — **P3, confirmed**
- **Evidence:** `electron/e2e.ts:74-94` calls `installCurseforge` directly with a `projectId`, then manually `createServer`, `ensureJava`, `writeEula`, `launchCommand` and `startWithAutoFix` — bypassing `Pipeline.preview/install`, `writeSidecar`, report DTO, cancel and store rollback; `ipc-test.ts:107-115` only asserts the Create screen renders; `mgmt-test.ts` has no installer coverage; no fixtures for route B, staging, EULA, cancel, hashes or traversal.
- **Symptom:** the P3 "E2E PASS" statement cannot support the pipeline claims (sidecar, CF project preview, route B, cancel, publish) that production uses.
- **Root cause:** the E2E harness was written around the spike engines before the pipeline existed and was never extended when the pipeline/sidecar/cancel layers were added; there are no fixtures in `electron/` for negative paths.
- **Impact:** the regression class this audit found (INST-001/002/003/005) passes green; future changes to preview/install DTOs have no gate, so "PORT COMPLETE — E2E PASS" overstates verification.
- **Fix:** drive CF key-mode and route B through `handlers.modpack_pipeline_preview/install`; add offline fixtures (synthetic `.mrpack`, server ZIP, client manifest with a 403 file) and negative tests (hash mismatch, cancel, EULA).
- **Verification:** run the new e2e; it must fail against the current implementation for INST-002/INST-003/INST-005.

### INST-023 — Runtime data writes into the source/app tree — **P3, confirmed**
- **Evidence:** `curated.ts:59-66` and `curated.ts:23-26` make the installer data directory both read and write target; `data/env-overrides-learned.json` is tracked by git; `paths.ts:8-15` correctly separates the data root but the installer ignores it; no packaging resource mapping exists (`package.json:7,11-12`).
- **Symptom:** dev runs dirty the working tree; packaged builds cannot persist learned data; data updates require a rebuild.
- **Root cause:** the spike used `import.meta.dirname`/`__dirname` for both immutable seed data and mutable learned state; the port kept that single location instead of splitting read-only resources from `<dataRoot>` state.
- **Impact:** dirty git state in development, guaranteed write failures when packaged (read-only install dir), and no way to ship data updates without a rebuild.
- **Fix:** read seeds from packaged resources, write mutable derivate under the data root; keep seeds immutable/tracked and learned data untracked.
- **Verification:** install crash pack in dev → `git status` clean; learned file appears under `.app-data`.

## Open questions

1. **Target contract on boot L2/L3 vs install-time verification:** should the app keep the spike's "verify at first user start" model (as the E2E and `server-process.ts` do), or adopt the Rust/`specs.md` M-10 requirement of a verified `Done (` *before* install success? The two can coexist, but INST-002/INST-016 need a decision on where the 4-layer defense lives.
2. **Is L4 (`itzg` MIT seed + hand overrides + learned) in scope for the product at all?** It is committed as part of the port (commit message "curated L4 data") and claimed 4-layer defense, but it is neither bundled nor reachable in builds and its pack keys can't match. If it is out of scope for licensing reasons, the docs/E2E claims need correcting instead of shipping dead data.
3. **CurseForge keyless posture:** the reference requires a one-time explicit opt-in, mode indicator and 2 req/s cap (D-25, `curseforge-policy.md:121-133`). The Electron app has none and issues unthrottled keyless metadata calls. Is that acceptable to the owner, or is the opt-in UI planned in another task?
4. **Route B policy reversal:** the uncommitted diff changes the CF client-export classification from "unsupported; use the author's SERVER pack" to "installable keylessly". That contradicts ADR-0012 and `docs/specs/modpack-server-setup-overhaul.md:21`. Which policy governs, and who approved the change?
5. **Dependency injection policy conflict:** the spike's L3 auto-fetch is the port's source of truth (`docs/electron-port-plan.md:48-49`), while the dormant Rust/ADR-0015 and overhaul spec explicitly forbid fetching by mod id. Which behavior should the audited app keep for Modrinth, and should CF remain prune-only?
6. **CurseForge API key accessibility:** the app only reads `<dataRoot>/curseforge-key.txt` with a process-lifetime cache; there is no settings UI or key validation. Is manual file placement the intended v1 UX, and should `safeStorage`/settings be added before key-mode is advertised?
7. **`dist-electron` as the shipped artifact:** is there an out-of-repo packaging step (electron-builder/NSIS) that copies `installer/data` and resources? None is present in this repo; if one is planned, the build contract must be documented and added to the gate.
8. **Update/ownership flow:** the Rust overhaul spec (`docs/specs/modpack-server-setup-overhaul.md:44-46`) and ADRs 0016/0017 define plan/report/managed-files/launch-config and managed-file ownership; the Electron port writes none of them and has no update command. Should the audit treat these as deferred (and record that), or are they expected in this migration?
9. **Quilt:** ADR-0005 removed Quilt new-install support; the renderer blocks it but `Pipeline.install` would still install a Quilt preview via IPC. Is a server-side rejection required for v1?
10. **Unicode paths:** the Rust pipeline fixed a Windows free-space call with a `™`-leaf path; the Electron port relies on Node/`fs` and does not normalize archive separators/UTF-8 flags. Should the Lead include a non-ASCII local pack/`.zip` case in the acceptance sweep to confirm there is no regression?
